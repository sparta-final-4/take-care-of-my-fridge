# Jev on 모드 상담 의도 평가

상태: **통과 기준 미달 (고치기 코드는 지우지 않음)** · 작성일: 2026-11-17 · 브랜치: `feat/chat-jev-shadow`

> 의도 선택지를 고친 재평가는 [jev-on-v2](#jev-on-v2-의도에서-빼기와-이어서-다시를-구분-2026-11-17) 절에 있다 (반대 허용 기준 112/121, all-on 대비 −8).
> 요리 이름 칸 정의·되돌림의 넓은 요청·이어짐을 따로 묻기를 반영한 3차 평가는 [jev-on-v3](#jev-on-v3-요리-이름-칸-정의-되돌림의-넓은-요청-이어짐을-따로-묻기-2026-11-17) 절에 있다 (반대 허용 기준 112/121, all-on-v2 대비 −8, 통과 못 함).
> 특정 분류 좁히기·이어짐 질문·요리 이름이 없으면 1등 분류·확인용 세트를 반영한 4차 평가는 [jev-on-v4](#jev-on-v4-특정-분류-좁히기-이어짐-질문-바꾸기-요리-이름이-없으면-1등-분류-확인용-세트-2026-11-17) 절에 있다 (기본 세트 반대 허용 113/121, all-on-v3 대비 −7로 통과 못 함 / 확인용 세트 차이 0으로 통과).
> 메시지의 키워드 줍기·정식 이름·1등 분류 확률 기준·확인용 세트 45문장을 반영한 5차 평가는 [jev-on-v5](#jev-on-v5-메시지의-키워드-줍기-정식-이름-1등-분류-확률-기준-확인용-세트-45문장-2026-11-17) 절에 있다 (확인용 세트 차이 0으로 통과, 기본 세트는 엉뚱한 결과 F11 1개로 통과 못 함 — F11은 실패로 인정한 문장).

on 모드(Jev가 의도·요청 종류·맛을 정하고, Jev 의도 confidence < 0.8이거나 실패하면 보정 없는 OpenAI 결과를 쓰며, 서버 보정은 서비스 규칙만)로
상담 의도를 정하는 전체 흐름을 평가 세트로 돌려 지금 서비스(all-on, OpenAI + 보정 전체)와 비교했다. 설계: [jev-on-design.md](jev-on-design.md) 8절.

## 결론

| 물음 | 답 |
|---|---|
| 통과 기준(all-on 대비 3문장 이내) | **통과하지 못했다.** 같은 121문장에서 all-on 120, jev-on **102**(−18). 매운맛-순한맛 반대 답 6문장을 맞음으로 쳐도 108(−12)이다 |
| intent 폴더 고치기 코드 삭제 | **하지 않았다.** 통과 기준이 조건이었다 |
| 맛 단계(keep-other-tastes·spoken-tastes-only)를 빼도 되나 | **on 모드 안에서는 거의 차이가 없다.** jev-on 102 → 101(−1: T10, 3회 중 1회만 맞음. T10은 jev-on에서도 3회 중 2회가 OpenAI 되돌림이라 흔들림). 다만 on 모드 자체가 통과하지 못해 지금 TasteWordChecker를 지울 근거는 아니다. 다시 추천 맛 따르기(refine-spoken-tastes)·밀키트·분류 부정어도 TasteWordChecker를 쓴다 |

틀린 18문장의 원인은 다섯 가지다(아래 표).
1. **OpenAI 되돌림 + 고치기 보정 없음 (6문장)**: Jev confidence가 낮은 문장은 대개 OpenAI도 틀리는 문장이고, all-on에서는 보정이 그걸 고쳤다(R14·R15·R17·N08·F11·T17). 되돌린 회차의 정답률은 63%(54회차 중 34)다.
2. **Jev 맛: 매운맛 ↔ 순한맛 반대 (6문장)**: Jev는 "매운 거 말고"에 순한맛 원함, "매운 거 먹고 싶어"에 순한맛 피함을 붙인다(T01·T03·T08·T13·U01·U04). 이 평가는 all-on과 같은 기준이라 틀림으로 셌다(Jev 평가에서는 허용한 기준).
3. **Jev 판단 (4문장)**: 의도 P01(당근 사고 싶어 → 추천 0.94), F12(조미료 뭐 있어 → 일반 0.88), 요청 종류 R05(차가운 면 → 특정 요리), U03(국물 말고 볶음으로 → 넓은 요청).
4. **"○○ 같은 요리" 요리 이름 채우기를 건너뜀 (1문장, 되돌림의 T17 포함 2문장)**: R06은 OpenAI가 요리 이름을 비우자 넓은 요청으로 가서, 넓은 요청 요리 이름도 "김피탕 같은 요리" → 찌개류로 엉뚱하게 받았다.
5. **요청 종류 규칙 (1문장)**: R01 "김치찌개 먹고 싶어"는 특정 요리라 분류를 쓰지 않는데, 기대값에 분류 [찌개]가 있다. 기대값을 고칠지 검토가 필요하다.

## 측정 조건

- 평가: `ChatIntentEvalManualTest`, 평가 세트 `chat-intent-eval.yml`(122문장, P12 포함) × 3회 다수결. gpt-4o-mini(의도·넓은 요청 요리 이름), Jev `jev-1.14.0`.
- `OPENAI_INTENT_EVAL_JEV_MODE=on`: 실제 JevIntentShadow(on)·JevIntentClassifier·JevIntentResolver·OpenAiSimilarDishGenerator(넓은 요청 프롬프트)를 만든다(`ChatIntentEvalJevOn`). 넓은 요청 요리 이름 캐시는 메모리(같은 표현이면 다시 부르지 않아 문장마다 첫 회차만 AI 호출).
- 기대 kind가 넓은 요청(BROAD)인 17문장은 분류·키워드 기대값 대신 "Jev로 정했고 쓴 요청 종류가 BROAD, 요리 이름이 비어 있지 않음"으로 비교했다. 요청 종류 일치는 따로 셌다(일치 판단에는 넣지 않음).
- 맛은 all-on과 같은 엄격한 기준(매운맛-순한맛 반대 답도 틀림)이다.
- `jev-on-no-taste-steps`: 같은 on 모드에 `OPENAI_INTENT_EVAL_SKIP_TASTE_STEPS=true`(보정 스위치 keep-other-tastes·spoken-tastes-only를 끔. main 코드는 그대로).
- all-on·all-off는 2026-11-16 결과(121문장, kind·P12 추가 전). 비교 표는 네 결과에 모두 있는 121문장으로 셌다. P12 "지금 세일하는 밀키트 있어?"는 jev-on·no-taste-steps 모두 맞음.
- 결과 파일: [eval-results/jev-on](eval-results/jev-on/), [eval-results/jev-on-no-taste-steps](eval-results/jev-on-no-taste-steps/) (summary·cases. runs.csv는 커밋하지 않음)

## jev-on-v2: 의도에서 빼기와 이어서 다시를 구분 (2026-11-17)

jev-on에서 되돌린 문장 중 R15 "오이 빼고 반찬 추천해줘"는 Jev가 REFINE(0.70)으로 답했다. "말고·빼고"가 든 문장(T17·T03·T08·T10)에서도 같았다.
원인은 두 가지로 봤다. ① 직전 추천이 없는데도 REFINE·RECIPE_DETAIL을 선택지로 줘서 고를 수 없는 답에 확률이 나뉘었다. ② REFINE 설명이 "빼 달라는 말"처럼 읽혔다.
빼기(피할 맛, 뺄 재료·분류)는 의도가 아니라 추천의 조건이다(피할 맛은 Jev 맛 질문, 뺄 재료·분류는 OpenAI가 꺼낸 값).

바꾼 것 (`JevFirstQuestions`):
- 직전 추천이 없으면 의도 선택지에서 REFINE·RECIPE_DETAIL을 뺀다(7개). 있으면 9개. 직전 추천이 없을 때의 REFINE·RECIPE_DETAIL → RECOMMEND 규칙은 안전망으로 남겼다(답은 모든 선택지로 읽는다).
- REFINE 이름 "조건 바꾸기" → "이어서 다시". 설명: "[직전 추천]에 이어서 하는 말. 직전 추천을 보고 다른 것을 달라거나, 직전 추천의 조건을 조금 바꿔 달라는 말이다. 무엇을 빼 달라는 말이라도 직전 추천과 상관없이 새로 요리를 정해 달라는 말이면 추천이다"

## jev-on-v3: 요리 이름 칸 정의, 되돌림의 넓은 요청, 이어짐을 따로 묻기 (2026-11-17)

jev-on-v2에서 남은 9문장(R01·R05·R06·T17·R17·N08·F11·P01·U03)과 이어지는 말의 되돌림(U09·U16)을 사용자가 정한 방향으로 고쳤다.
**방향**: Jev 쪽 추천은 하나의 의도(추천)로 보고, 빼기(피할 맛·뺄 재료·뺄 분류)와 이어짐(직전 추천에 이어지는 말인지)은 추천 안의 항목으로 다룬다.
추천 뒤 흐름을 건드리지 않으려고 "추천 + 이어짐"은 안에서만 ChatIntent.REFINE으로 넘긴다. 단어 목록은 넣지 않고 뜻으로만 고쳤다.

바꾼 것:
1. `prompts/chat-intent.txt` dishText 정의: "사용자가 원하는 요리이거나, 비슷한 것을 찾을 기준으로 말한 요리의 이름. '○○ 같은 것'의 ○○도 여기에 쓴다. 빼 달라거나 피하고 싶다고 말한 요리는 쓰지 않는다. '말고'·'빼고'가 맛이나 재료에 붙었으면 요리 이름은 그대로 쓴다. 분류나 종류(찌개, 국물, 디저트)와 재료 이름은 요리 이름이 아니다"에 일반 예시 하나("짠 거 말고 된장찌개 같은 거" → 된장찌개 / "된장찌개 말고 다른 거" → 빈 문자열)를 더했다. 예전 "분류·요리 종류(…)나 특징(…)은 요리 이름이 아니라 빈 문자열이다" 줄은 새 정의로 바꿨다. 프롬프트는 2,919자에서 3,038자가 됐다(3,300자 기준 안이라 다른 문장은 줄이지 않았다). off 모드도 이 프롬프트를 쓴다.
2. 되돌림의 넓은 요청: Jev 의도 confidence가 0.8 미만이라 OpenAI로 되돌릴 때, OpenAI 의도가 추천 계열(RECOMMEND·REFINE)이고 이미 받아 둔 Jev 2차 요청 종류가 넓은 요청이면 의도·맛은 OpenAI 것으로 두고 넓은 요청 요리 이름 경로(LLM 요리 이름 → 검색)를 탄다. OpenAI를 다시 부르지 않는다. decision은 `OPENAI_LOW_CONFIDENCE_JEV_BROAD`다.
3. Jev 설명: 1차 "추천"에 "재료를 사고 싶다는 말은 추천이 아니라 장보기다", 2차 "특정 분류"에 "빼거나 피하는 말이 함께 있어도, 원하는 요리 종류를 하나 말했으면 특정 분류다"를 더했다.
4. 특정 요리에도 Jev 1등 분류를 넣는다(1등이 없음이면 넣지 않는다). 분류는 점수를 올리는 조건이라 같은 분류가 앞에 온다.
5. 1차 의도 선택지에서 "이어서 다시"를 뺐다(직전 추천이 있어도). 추천 설명은 새 추천과 이어서 받는 추천을 모두 포함한다. 직전 추천이 있을 때만 Noul `follows_previous`("[직전 추천]에 이어서 하는 말인가? …")를 더 묻고, 추천 + follows_previous ≥ 0.5(평가로 정할 상수)면 REFINE으로 넘긴다. 의도 confidence는 "추천" 선택지의 confidence다. 레시피 자세히는 직전 추천이 있을 때만 선택지로 남는다. 비교 로그에 `jevFollowsPrevious` 칸을 더했다.

평가 비교 기준: 특정 요리 문장은 기대값에 분류가 있으면 1등 분류와 비교하고(R01), 없으면 분류를 비교하지 않는다.
평가는 all-on-v2(off 모드, 보정 모두 켬 = 지금 서비스, dishText 정의만 바뀜)와 jev-on-v3(on 모드)를 122문장 × 3회 돌렸다. 결과: [eval-results/all-on-v2](eval-results/all-on-v2/), [eval-results/jev-on-v3](eval-results/jev-on-v3/).

| 통과 기준(all-on-v2 대비 3문장 이내, 맛은 반대 허용) | **통과하지 못했다.** all-on-v2 120, jev-on-v3 **112**(−8). 엄격 기준은 105(−15) |

- 이번 변경으로 5문장(R01·T17·N08·P01·U03)이 풀렸고 4문장(T02·T11·T16·U09)이 새로 틀렸다. 새로 틀린 넷은 모두 이번 변경의 부작용이다. 특정 분류 설명을 "빼는 말과 함께 원하는 종류를 말한 경우"로 좁히고, 이어짐 기준을 평가로 정하면(0.6이면 이 세트에서 U09가 풀림) 되돌릴 수 있다.
- 남은 원인: Jev 요청 종류(R05), OpenAI 요리 이름 꺼내기(R06: "○○ 같은 요리"의 ○○을 정의대로 쓰지 않음), OpenAI 되돌림(R17·F11).

### 지연·비용 (360회차, 캐시 할인 전)

- jev-on-v3 의도 결정까지 ms: 중앙값 1,264 / 95% 2,113 / 최대 3,893. 넓은 요청 AI 호출(캐시 미스)은 2,113 / 2,535 / 2,954.
- jev-on-v3 비용: OpenAI 의도 $0.1335(입력 778,764·출력 27,758토큰), 넓은 요청 요리 이름 20번 $0.0013, Jev $0.0301. 메시지당 약 $0.00046.

### 정리 단계에서 할 일 (남은 일)

- on이 통과해 off를 지울 때 **REFINE을 ChatIntent와 OpenAI 프롬프트에서 없애고 추천의 이어짐 항목으로 바꾼다.** 지금은 JevIntentClassifier가 "추천 + 이어짐"을 안에서만 REFINE으로 넘기고(JevIntentResolver는 그 의도를 그대로 씀), OpenAI 프롬프트(chat-intent-followup.txt)는 아직 RECOMMEND와 REFINE을 따로 답한다.

## jev-on-v4: 특정 분류 좁히기, 이어짐 질문 바꾸기, 요리 이름이 없으면 1등 분류, 확인용 세트 (2026-11-17)

jev-on-v3에서 남은 문제를 사용자가 정한 방향으로 고쳤다. 단어 목록이나 단어 예시는 넣지 않고 뜻으로만 고쳤고, 평가 세트 문장은 예시로 쓰지 않았다.
R17(주식 동음이의어)·F11은 실패로 인정하고 고치지 않았다.

바꾼 것:
1. 2차 요청 종류 설명: "특정 분류"를 "요리의 종류를 말했고, 그 종류가 분류 목록의 하나에 맞는다(찌개, 디저트처럼). 빼거나 피하는 말이 함께 있어도 이 기준은 같다"로 바꾸고, "넓은 요청"에 "말한 종류가 여러 분류에 걸치면 넓은 요청이다"를 더했다.
2. `follows_previous` 질문을 서버의 REFINE 뜻(직전 조건을 이어받음)에 맞췄다: "[직전 추천]의 조건(맛, 재료, 종류)을 이어받으면서 일부만 바꿔 달라는 말인가? 직전 추천을 보고 조건을 더하거나 빼거나 바꿔 달라는 말이면 예다. 직전 추천에 덧붙여 말했어도 직전 조건과 상관없이 새로 요리를 정해 달라는 말이면 아니오다". 기준 0.5는 그대로다.
3. Jev 요청 종류가 특정 요리인데 최종 요리 이름이 비면(OpenAI가 비웠거나 메시지에 그대로 없음), Jev 1등 분류가 있으면 특정 분류 경로로 그 분류를 쓰고, 없음이면 지금처럼 넓은 요청으로 간다. 맛·재료 칸은 그대로 넘긴다. 비교 로그는 `jevRequestKind`(Jev 원래 답)와 `jevUsedKind`(바뀐 뒤 쓴 종류)를 따로 남긴다.
4. `prompts/chat-intent.txt` dishText 정의 첫 줄에 "처음 듣는 요리 이름이어도 사용자가 말한 그대로 쓴다"를 넣었다. 같은 뜻의 아래 줄 문장("처음 듣는 이름이어도 말한 그대로 쓴다")은 겹쳐서 지웠다. 3,038자 → 3,046자(3,300자 기준 안, 다른 문장은 줄이지 않음).
5. 확인용 문장 세트 `src/test/resources/chat-intent-holdout.yml`(새 문장 15개)과 평가 옵션 `OPENAI_INTENT_EVAL_SET=main|holdout`(기본 main)을 더했다. 이 세트 결과를 보고 프롬프트나 설명을 고치지 않는다.

평가: 기본 세트 122문장 × 3회로 all-on-v3(off, 보정 모두 켬)와 jev-on-v4(on), 확인용 세트 15문장 × 3회로 all-on-holdout과 jev-on-holdout.
결과: [all-on-v3](eval-results/all-on-v3/), [jev-on-v4](eval-results/jev-on-v4/), [all-on-holdout](eval-results/all-on-holdout/), [jev-on-holdout](eval-results/jev-on-holdout/).

### all-on-v2 → all-on-v3 (dishText에 처음 듣는 이름 문장, off 모드)

## jev-on-v5: 메시지의 키워드 줍기, 정식 이름, 1등 분류 확률 기준, 확인용 세트 45문장 (2026-11-17)

김피탕 확인(`김피탕 같은 요리 추천해줘`에서 OpenAI가 요리 이름을 비우고 키워드에만 넣음, Jev 1등 분류가 국)과 jev-on-v4의 남은 문제를 사용자가 정한 방향으로 고쳤다.
단어 목록이나 단어 예시는 넣지 않았고, 평가 세트 문장은 예시로 쓰지 않았다. 통과 기준도 사용자가 바꿨다(결론 참고).

바꾼 것:
1. **메시지의 키워드 줍기 (on)**: Jev 요청 종류가 특정 요리인데 최종 요리 이름이 비면, OpenAI 키워드 중 메시지에 글자 그대로(띄어쓰기 무시) 있는 첫 키워드를 요리 이름으로 쓴다. 메시지에 없는 키워드(OpenAI가 덧붙인 비슷한 요리)는 쓰지 않는다. 비교 로그 `jevUsedReason=DISH_FROM_KEYWORD`.
2. **정식 이름**: 비슷한 요리 호출(`prompts/chat-similar-dishes.txt`)에 `formalName` 칸("요리 이름이 줄임말이면 정식 이름을 쓴다. 줄임말이 아니거나 모르면 빈 값이다.")을 더했다. 검색 순서는 요리 이름 → 정식 이름(있고 요리 이름과 다를 때) → 비슷한 요리이고, 정식 이름으로 맞은 레시피는 요리 이름과 같은 순위(`KeywordMatch.NAME`)다.
   - 호출 수는 그대로다: 비슷한 요리 호출 조건(ES 경로에서 요리 이름 그대로 맞은 레시피가 없을 때)이 정식 이름이 필요한 경우와 같아서 조건을 바꾸지 않았다. 같은 호출 하나로 정식 이름도 받는다.
   - 캐시 값이 목록에서 객체(`{formalName, dishes}`)로 바뀌어 키 버전을 올렸다: `chat:similar-dishes:v4:`, `chat:broad-dishes:v2:`(넓은 요청은 정식 이름이 없지만 값 모양을 같게 했다).
   - **글자 순서 확인(사용자 결정으로 더함)**: 받은 줄임말의 글자가 정식 이름에 순서대로 다 있지 않으면 정식 이름을 버린다(김볶밥 → 김치볶음밥은 쓰고, 김피탕 → 김치찌개는 버림). gpt-4o-mini가 김피탕의 정식 이름을 5번 모두 "김치찌개"로 답해, 그대로 두면 김치찌개 레시피가 말한 요리처럼 맨 앞에 오기 때문이다(아래 끝에서 끝 확인).
3. **Jev 1등 분류 확률 기준** `JevIntentResolver.MIN_CATEGORY_CONFIDENCE = 0.7`(평가로 정함): 특정 요리는 기준 미만이면 분류를 넣지 않고, 특정 분류와 "요리 이름이 없어 1등 분류로 가기"(jev-on-v4 결정 3)는 기준 미만이면 넓은 요청으로 간다. 비교 로그에 1·2등 분류와 확률(`jevCategory`·`jevCategoryConfidence`·`jevCategory2`·`jevCategory2Confidence`)을 남긴다.
4. **이어짐 기준** 0.5 → **0.45**.
5. **요리 이름 칸의 분류 이름 (on)**: OpenAI 요리 이름이 DB 분류 이름(Jev 분류 선택지와 같은 목록)과 같으면 요리 이름으로 쓰지 않고 그 분류로 찾는다(`DISH_IS_CATEGORY`, H04 "죽").
6. 2차 "특정 분류" 설명을 jev-on-v2 때("요리의 종류를 하나 말했다(찌개, 디저트처럼)")로 되돌렸다. "넓은 요청"의 "말한 종류가 여러 분류에 걸치면 넓은 요청이다"는 남겼다.
7. `chat-intent.txt` 예시의 "→ dishText: 빈 문자열" 4곳을 "→ dishText는 비운다"로 바꿨다(OpenAI가 "빈 문자열"을 값으로 베낀 U12). 3,046자 → 3,038자.
8. 확인용 세트를 45문장으로 늘렸다(H16~H45 30문장 추가, 기존 15문장 그대로). 구성: 특정 요리 5(줄임말만 친 문장 H16·H17), "○○ 같은 요리" 4(줄임말 H24), 특정 분류 4, 넓은 요청 5(여러 분류 H32·H33), 맛·재료 빼기 4, 이어지는 말 4(이어받기 H38·H39, 새 추천 H40·H41), 추천 아님 4.

### off 모드에서 김피탕이 처리되던 경로 (jev-on-v4 커밋 a71f40cb, off 모드)

같은 확인을 결정 2 이전 코드로 off 모드에서 돌렸다.
1. 의도: OpenAI 추천, 요리 이름 김피탕(4문장 모두. "같은 요리"는 서버 보정이 첫 키워드·"○○ 같은"으로 채움).

3. 탕수육은 비슷한 요리 깐풍기·유린기·춘권·팔보채를 받아 늘린 이름(EXPANDED)으로 깐풍기·유린기·춘권을 찾는다. 김피탕에서 탕수육·유린기로 가는 길은 비슷한 요리 AI가 김피탕을 알 때뿐이고, gpt-4o-mini는 지금 모른다.
