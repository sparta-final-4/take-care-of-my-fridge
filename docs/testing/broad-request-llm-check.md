# 넓은 요청 LLM 요리 이름 확인

상태: 확인만 함 (기능 코드 변경 없음) · 작성일: 2026-11-16 · 브랜치: `feat/chat-jev-shadow`

넓은 요청("술안주", "반찬")을 분류 묶음 사전 없이 처리하려고, LLM에게 요청에 맞는 흔한 요리 이름을 받아 기존 키워드 검색으로 찾는 방법을 확인한다.
[벡터 검색](vector-broad-request-check.md)은 맞는 결과가 40% 안팎이라 쓸 수 없었다.
김피탕처럼 레시피에 없는 요리 이름에 쓰는 비슷한 요리 호출(`SimilarDishFinder`, `OpenAiSimilarDishGenerator`, `prompts/chat-similar-dishes.txt`)과 같은 방식이다.

> 판정(○ 맞음 · △ 부분 · ✗ 틀림)은 AI 보조(Claude)가 레시피 이름·분류만 보고 내린 것이다. 사람이 다시 확인해야 한다.
> 아래 "결론"은 첫 프롬프트(v1) 기준이다. 넓은 요청 전용 프롬프트로 다시 확인한 결과는 [프롬프트 v2](#프롬프트-v2-넓은-요청-전용) 절에 있다.

## 결론

| 물음 | 판단 |
|---|---|
| 이 방식으로 넓은 요청을 처리할 수 있나 | **대체로 된다. 다만 그대로는 못 쓴다.** 요리 이름이 나온 요청은 찾은 레시피(이름마다 상위 3개)의 80%대가 맞다(124개 중 ○ 104, 반찬은 이름이 나온 2회 목록). 벡터(같은 요청 ○ 43/100)보다 확실히 낫다. 문제는 세 가지다. ① 빈 목록: "다이어트 메뉴"는 3회 모두, "반찬"은 3회 중 2회 빈 목록이었다. ② 키워드 검색에 없는 이름: 소세지구이·토스트·핫윙·미역줄기볶음과 캠핑 요리의 설명형 이름("그릴에 구운 고기", "캠핑용 볶음밥")은 0건이다. ③ 너무 넓은 이름: "치킨"(치킨롤·삼계치킨), "김치"(117건), "샐러드"(93건), "디저트"(분류 이름)는 키워드 검색 순위가 기대와 다르다 |
| 김피탕용 프롬프트와 같이 쓸 수 있나 | **따로 둔다.** 받는 것이 다르다(요리 이름 → 비슷한 요리 / 요청 → 맞는 요리). 김피탕용 규칙 중 "받은 요리 이름 자신은 쓰지 않는다", "오타면 고친 이름을 맨 앞에"는 넓은 요청에 맞지 않는다. "확실히 모르면 빈 목록"은 김피탕용에서는 지어낸 이름을 막지만, 넓은 요청에서는 반찬·다이어트 메뉴를 빈 목록으로 만들었다. 출력 모양(JSON `dishes`), 호출 클래스, 레시피 사이트에 흔한 이름·설명 말 금지 규칙은 같이 쓸 수 있다 |
| temperature 0이면 결과가 같나 | **아니다.** 12개 중 7개만 3회가 같았다. 반찬(빈 목록 ↔ 5개), 캠핑 요리(1회와 2·3회가 다름), 간식·손님 초대·따뜻한 국물(한 이름만 바뀜)이 달랐다 |

- 지금 OpenAI 의도 판단은 넓은 요청에서 요리 이름을 거의 뽑지 않는다(아래 1). 분류(칸 `categories`)나 "칼칼한 국물", "매운국" 같은 표현을 낸다. T02만 3회 중 2회 매운탕·김치찌개·칼국수를 냈다.
- 이 방식을 쓰려면 넓은 요청용 프롬프트에서 빈 목록 규칙을 "요리를 원하는 말이 아니면 빈 목록"으로 좁히고, 이름이 0건이거나 너무 넓을 때(분류 이름, 수십 건)를 다루는 규칙이 더 필요하다. 이 문서는 확인만 했고 정하지 않았다.

## 2·3. LLM 요리 이름과 키워드 검색

### 측정 조건

- 일회용 Node 스크립트(커밋하지 않음). OpenAI `/v1/chat/completions`, `gpt-4o-mini`, `temperature` 0, `response_format` JSON. 키는 `OPENAI_INTENT_EVAL_KEY`.
- 요청마다 3회. 36회 합계 9,095토큰.
- 일회용 시스템 프롬프트 (`chat-similar-dishes.txt`의 원칙을 따름):

```
너는 음식 요청을 받아 그 요청에 맞는 흔한 요리 이름을 정해진 JSON으로만 낸다. 답은 하지 않는다.
- dishes: 요청에 맞는 흔한 요리 이름 5개. 요청이 무엇을 원하는지 확실히 모르면 dishes를 빈 목록으로 낸다.
- 요리 이름만 쓴다. 분류 이름("국", "찌개", "튀김", "디저트", "반찬"), 번호는 쓰지 않는다.
- 요리를 설명하는 말("중국식 ~", "매운 ~ 볶음")은 쓰지 않는다.
- 레시피 사이트에 흔히 있는 일반적인 요리 이름을 쓴다. 가게 이름·브랜드 이름은 쓰지 않는다.
예) 해장 → dishes: 콩나물국, 북엇국, 해장국, 순두부찌개, 우거지국
JSON 모양: {"dishes": ["…"]}
```

- 키워드 검색은 `RecipeSearchService.keywordRequest`와 같게: `name^3`·`ingredients.text^2`·`summary`, `cross_fields`, AND, 정렬 RELEVANCE(`_score`, `id` 내림차순). 필터 없음, 벡터 없음. 로컬 ES `recipes` 1,693건.
- "찾힌 이름 수"는 대표 목록(3회 중 가장 많이 나온 목록)의 이름 중 1건 이상 찾힌 수다. "맞는 레시피"는 이름마다 상위 3개(찾힌 만큼)를 합친 것 중 요청에 맞는 수다.

### 보인 문제

- **빈 목록**: "확실히 모르면 빈 목록" 규칙 때문에 반찬(2/3)·다이어트 메뉴(3/3)가 빈 목록이었다. 김피탕용에서는 지어낸 이름을 막는 규칙이지만, 넓은 요청은 "모르는 요리"가 아니다.
- **0건 이름**: 레시피 이름 표기가 다르거나(소세지구이 ↔ 소시지, 핫윙 ↔ 닭날개) 레시피가 없다(토스트, 미역줄기볶음). 캠핑 요리는 설명형 이름("그릴에 구운 고기", "캠핑용 볶음밥")을 내서 규칙을 어겼다.
- **너무 넓은 이름**: 치킨(치킨롤·삼계치킨이 위), 김치(117건), 샐러드(93건), 스테이크(43건)는 키워드 검색 순위가 요청과 맞지 않을 수 있다. "디저트"는 분류 이름인데 나왔다.
- **같은 요리가 겹침**: 따뜻한 국물 요리·국물·칼칼한 국물이 거의 같은 목록(김치찌개·순두부찌개)이다. 결과는 맞지만 매번 같은 레시피가 나올 수 있다.

## 프롬프트 v2 (넓은 요청 전용)

위(v1)에서 보인 문제(빈 목록, 너무 넓은 이름, 설명형 이름, 분류 이름)를 넓은 요청 전용 프롬프트로 고쳐 다시 확인했다.
나중에 `prompts/chat-broad-dishes.txt`로 쓸 초안이다. 김피탕용(`chat-similar-dishes.txt`)과 따로 둔다. 단어 목록을 늘리지 않고 뜻으로 적었고, 예시는 평가 요청이 아닌 것 1개만 넣었다.

```
너는 음식 요청을 받아 그 요청에 맞는 요리 이름을 정해진 JSON으로만 낸다. 답은 하지 않는다.
- dishes: 요청에 맞는 요리 이름 5개. 요청이 넓거나 흐려도, 그 말을 들은 사람이 떠올릴 만한 요리를 고른다. 요리·음식을 원하는 말이 아닐 때만 빈 목록으로 낸다.
- 레시피 사이트에서 레시피 제목으로 흔히 쓰는 구체적인 요리 이름을 쓴다. 이름 하나가 요리 하나를 가리켜야 한다. 여러 요리를 묶어 부르는 말(요리 분류, 재료 이름 하나, 음식 종류)은 쓰지 않는다.
- 요리 이름에 만드는 방법·먹는 곳·때를 설명하는 말을 붙이지 않는다. 요리 이름만 쓴다.
- 서로 다른 종류의 요리를 고른다. 같은 요리에서 재료만 바꾼 것을 여럿 내지 않는다.
- 가게 이름·브랜드 이름은 쓰지 않는다.
예) 비 오는 날 → dishes: 김치전, 수제비, 부대찌개, 감자전, 어묵탕
JSON 모양: {"dishes": ["…"]}
```
