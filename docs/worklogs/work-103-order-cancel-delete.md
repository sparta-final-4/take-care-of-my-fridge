# WORK-103: 결제 시도 없는 주문의 취소 삭제와 주문 만료

상태: 검증 대기 · 작성일: 2026-10-27 · 담당: 준혁

## 목표와 완료 기준

- 결제를 시도하지 않은 결제 대기 주문은 취소하면 재고·번개 드롭 남은 수량·1인 구매 기록을 되돌리고 주문 상품과 주문을 지운다.
- 결제를 시도한 결제 대기 주문은 사용자가 취소할 수 없다. 409로 거절한다.
- 결제하기를 누르지 않고 떠난 주문은 생성 5분 뒤 주문 만료 스케줄러가 같은 방법으로 지운다.

## 근거와 범위

- 문제: 취소는 주문 상태만 취소로 바꾸고 행을 남겼다. 결제 시도가 없던 주문은 늦게 들어올 결제도, 남길 결제 기록도 없어 쓸모없는 행이 쌓였다. 탭을 닫아 취소 요청이 오지 않은 주문은 정리하는 곳이 없어 재고를 계속 붙잡았다.
- 결제를 시도한 주문은 결제 행이 주문을 참조해 지울 수 없다. 또 취소를 누른 순간 PG에서 결제가 끝나 있으면 취소가 아니라 환불로 가야 하는데, 주문 쪽은 이것을 판단할 수 없다. 이런 주문은 결제 쪽이 정리해 취소 상태로 남긴다. 그 정리는 이 작업 범위가 아니다.
- 지운 주문에 다시 취소가 오면 404다. 서버는 "방금 지운 주문"과 "원래 없던 주문"을 구분하지 않는다. 재고가 두 번 되돌아가지 않는 것은 주문 행 잠금이 보장한다.
- 이미 취소된 주문의 취소 요청에 같은 200을 주던 동작은 없어진다. 취소 상태 주문은 결제 쪽 정리로만 생기고, 다시 취소하면 `ORDER_008`이다.

## 구현 결과

- `OrderCancelService.cancel(memberId, orderId)`: 주문 행을 잠그고 결제 대기인지 확인한다(`ORDER_007`, `ORDER_008`). 결제 행이 하나라도 있으면 `ORDER_012`로 거절하고, 없으면 지운다.
- `OrderCancelService.expire(orderId)`: 스케줄러용이다. 잠근 뒤 주문이 없거나, 결제 대기가 아니거나, 결제 행이 있으면 예외 없이 건너뛴다.
- 지우는 순서는 재고·번개 드롭 남은 수량 되돌리기, 주문 상품 삭제, 주문 삭제다. 재고를 되돌리는 코드는 `OrderCancelService` 한 곳에 둔다. `restoreStock`이 주문 상품 목록을 받게 바꿔, 결제 쪽이 취소 상태로 남길 때도 같은 메서드를 쓸 수 있게 했다.
- 결제 행 확인은 결제 도메인의 조회 메서드 `PaymentService.hasPayment(orderId)`로 한다. 결제 상태와 상관없이 행이 있으면 결제 시도가 있었던 것으로 본다.
- 주문 행 잠금이 트랜잭션의 첫 조회라서, 결제 행 확인은 잠금을 얻기 전에 커밋된 결제까지 본다. 결제하기(`PaymentCommandService.create`)도 같은 주문 행을 잠그므로, 취소와 결제하기는 하나씩 처리된다.
- `OrderExpireScheduler`: 이전 실행이 끝나고 1분 뒤 다시 돈다. 생성 5분이 지난 결제 대기 주문을 id 순으로 100건씩 읽어 `expire`를 부른다. 결제 행은 조회에서 거르지 않고 `expire`가 잠근 뒤 본다. 한 건이 실패해도 로그를 남기고 다음 건을 처리한다.
- `PATCH /api/orders/{orderId}/cancel`은 경로는 그대로이고, 응답을 데이터 없는 200으로 바꿨다. 지운 주문에 돌려줄 상태가 없어 `OrderCancelResponse`를 지웠다.
- 새 ErrorCode: `ORDER_PAYMENT_ATTEMPTED`(`ORDER_012`, 409, 결제를 시도한 주문은 취소할 수 없습니다).
- DB 변경은 없다. 주문 만료 조회는 기존 `idx_orders_status_created_at`을 쓴다.

## 연결과 남은 작업

- 결제를 시도한 결제 대기 주문의 정리: 진행 중인 결제가 없고 마지막 결제를 만든 지 10분이 지나면 취소 상태로 바꾸고, 재고는 `OrderCancelService`의 메서드로 되돌린다. 그때까지 이런 주문은 결제 대기로 남고, 주문 만료 스케줄러가 매번 읽었다가 건너뛴다.
- 주문 확인 화면: 취소·나가기가 404, `ORDER_008`, `ORDER_012`를 받을 때와 결제하기가 404를 받을 때의 처리를 프론트에서 맞춘다.
- API 명세와 주문 도메인 문서를 새 동작에 맞춘다.
