# WORK-103: 결제 대기 주문의 주문 취소 삭제와 자동 정리

상태: 검증 대기 · 작성일: 2026-10-27 · 담당: 준혁

## 목표와 완료 기준

- 결제를 시도하지 않은 결제 대기 주문은 주문 취소하면 재고·번개 드롭 남은 수량·1인 구매 기록을 되돌리고 주문 상품과 주문을 지운다.
- 결제를 시도한 결제 대기 주문은 사용자가 주문 취소할 수 없다. 409로 거절한다.
- 주문 취소 요청 없이 남은 결제 대기 주문도 재고를 붙잡지 않게 서버가 정리한다.

| 상황 | 언제 | 무엇을 | 누가 |
|---|---|---|---|
| 결제하기를 안 누르고 주문 취소·나가기 | 바로 | 재고 되돌림 → 주문 삭제 | 주문 취소 API |
| 결제하기를 안 누르고 탭 닫기 등으로 떠남 | 생성 5분 뒤 | 재고 되돌림 → 주문 삭제 | 주문 만료 스케줄러 (주문 쪽) |
| 결제하기를 눌렀는데 끝내지 않음 (실패·결제창 닫기·만료) | 마지막 결제 뒤 10분 | 재고 되돌림 → 주문 취소 상태로 남김 (결제 기록 보존) | 결제 정리 스케줄러 (결제 쪽) |
| 결제하기를 누른 주문에 주문 취소 요청 | 바로 | 거절 (409 `ORDER_012`), 주문·재고 그대로 | 주문 취소 API |

## 근거와 범위

- 문제: 주문 취소는 주문 상태만 취소로 바꾸고 행을 남겼다. 결제 시도가 없던 주문은 늦게 들어올 결제도, 남길 결제 기록도 없어 쓸모없는 행이 쌓였다. 탭을 닫아 주문 취소 요청이 오지 않은 주문과 결제가 실패한 뒤 떠난 주문은 정리하는 곳이 없어 재고를 계속 붙잡았다. 결제 만료(`PaymentTimeoutScheduler`)는 결제만 실패로 바꾸고 주문은 건드리지 않았다.
- 결제를 시도한 주문은 결제 행이 주문을 참조해 지울 수 없다. 또 주문 취소를 누른 순간 PG에서 결제가 끝나 있으면 취소가 아니라 환불로 가야 하는데, 주문 쪽은 이것을 판단할 수 없다. 그래서 사용자의 주문 취소는 거절하고, 결제 상태를 아는 결제 쪽이 일정 시간 뒤 주문 취소 상태로 정리한다.
- 결제 실패 즉시 주문을 취소하지 않는다. 주문과 결제는 1:N이라 카드 거절이나 결제창을 닫은 사용자가 같은 주문으로 다시 결제할 수 있어야 한다. 기준은 결제 만료 시간(`PAYMENT_EXPIRE_MINUTES`, 10분)과 같게 두어, 결제창이 만료된 주문과 사용자가 결제창을 닫은 주문을 한 규칙으로 잡는다. 결제하기는 결제창을 띄우기 전에 결제 행을 만들므로 결제창이 뜨지 않은 주문도 결제를 시도한 주문이다.
- 지운 주문에 다시 주문 취소가 오면 404다. 서버는 "방금 지운 주문"과 "원래 없던 주문"을 구분하지 않는다. 재고가 두 번 되돌아가지 않는 것은 주문 행 잠금이 보장한다.
- 이미 취소된 주문의 주문 취소 요청에 같은 200을 주던 동작은 없어진다. 취소 상태 주문은 결제 쪽 정리로만 생기고, 다시 주문 취소하면 `ORDER_008`이다.

## 구현 결과

- `OrderCancelService.cancel(memberId, orderId)`: 주문 행을 잠그고 결제 대기인지 확인한다(`ORDER_007`, `ORDER_008`). 결제 행이 하나라도 있으면 `ORDER_012`로 거절하고, 없으면 지운다. 지우는 순서는 재고·번개 드롭 남은 수량 되돌리기, 주문 상품 삭제, 주문 삭제다.
- `OrderCancelService.expire(orderId)`와 `OrderExpireScheduler`: 1분마다 생성 5분이 지난 결제 대기 주문을 id 순으로 100건씩 읽는다. 건마다 주문 행을 잠그고, 지워졌거나 결제 대기가 아니거나 결제 행이 있으면 건너뛰고, 아니면 `cancel`과 같은 방법으로 지운다.
- `OrderCancelService.cancelAbandoned(orderId, lastPaymentBefore)`와 `PaymentTimeoutScheduler.cancelAbandonedOrders`: 1분마다 진행 중 결제(`READY`)가 없고 마지막 결제가 10분 전보다 이른 결제 대기 주문을 주문 id 순으로 100건씩 읽는다. 건마다 주문 행을 잠그고 조건을 다시 본 뒤 `Order.cancel()`로 취소 상태로 바꾸고 재고를 되돌린다. 결제 행은 남긴다.
- 재고를 되돌리는 코드는 세 경로 모두 `OrderCancelService.restoreStock` 한 곳이다. 두 스케줄러 모두 한 건이 실패해도 로그를 남기고 다음 건을 처리한다.
- 결제 데이터는 결제 도메인의 조회 메서드로 읽는다. `PaymentService.hasPayment`(결제 행이 있는지), `isAbandoned`(결제가 있고 `READY`가 없고 기준 이후 결제가 없는지), `findAbandonedOrderIds`(정리 대상 조회).
- 동시성: 주문 취소·주문 만료·결제 정리·결제하기(`PaymentCommandService.create`)·결제 승인은 모두 같은 주문 행을 먼저 잠근다. 잠금이 트랜잭션의 첫 조회라 결제 행 확인은 잠금을 얻기 전에 커밋된 결제까지 본다. 정리된 주문에 늦게 PG 결제가 들어오면 기존 승인 처리가 거절하고 보상 취소한다.
- `PATCH /api/orders/{orderId}/cancel`은 경로는 그대로이고, 응답을 데이터 없는 200으로 바꿨다. 지운 주문에 돌려줄 상태가 없어 `OrderCancelResponse`를 지웠다.
- 새 ErrorCode: `ORDER_PAYMENT_ATTEMPTED`(`ORDER_012`, 409, 결제를 시도한 주문은 취소할 수 없습니다).
- 쓰는 곳이 없어진 `Order.isCancelled()`를 지웠다. `PaymentCommandService.PAYMENT_EXPIRE_MINUTES`는 정리 스케줄러가 같은 값을 쓰도록 공개했다.
- DB 변경은 없다. 주문 만료 조회는 기존 `idx_orders_status_created_at`을 쓴다.
