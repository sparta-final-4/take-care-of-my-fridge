# WORK-107: 주문 확인 화면 결제창과 서버 확인

상태: 검증 대기 · 작성일: 2026-10-22 · 담당: 결제·환불

## 목표와 완료 기준

- 주문 확인 화면의 결제하기에서 PortOne 결제창을 띄운다.
- 결제창이 성공으로 끝나도 서버가 PG 결제를 확인(결제 확정 API)한 뒤에만 "결제 성공"을 보여 준다.
- 서버가 거절하면 성공 문구 없이 서버 메시지를 보여 준다.

## 근거와 범위

- PR: #193(결제창 열기, 10/22), #302 중 결제 부분(결제 확정 연결·회원 휴대폰 번호, 10/27).
- #193 때는 결제창 결과만 보고 성공을 띄웠고, 확정 연결은 후속으로 남겼다. #302에서 확정 응답까지 기다리도록 바꿨다.
- 결제 준비 API는 생성 클라이언트에 아직 없어 `domains/payment/api.ts`에서 직접 호출한다. 결제 확정은 생성 클라이언트(`paymentApi.confirm`)를 쓴다.

## 구현 결과

- `@portone/browser-sdk` 추가. `domains/payment/portone.ts`의 `openPaymentWindow`가 결제 준비 응답의 결제 ID·주문명·금액으로 결제창을 연다. 상점 ID·채널 키는 `VITE_PORTONE_STORE_ID`, `VITE_PORTONE_CHANNEL_KEY`로 받는다.
- 결제 ID를 40자로 만든다(`payment-` + 하이픈 없는 UUID). 처음 쓴 KG이니시스 주문번호(oid)가 40자까지만 받기 때문이다.
- `OrderCheckoutSection`의 결제 흐름: 결제 준비 → 결제창 → 결제창이 실패·취소면 그 메시지 → 성공이면 결제 확정 → 확정 성공에만 "결제 성공!" 후 메인으로 이동.
  - 서버가 거절하면(만료·금액 불일치·결제할 수 없는 주문) 서버 메시지를 띄운다.
  - 생성 5분이 지나 서버가 지운 주문(`ORDER_001`)이면 다시 주문하라고 안내하고 장바구니로 보낸다.
  - 결제를 마치고 떠나는 이동은 나가기 확인으로 붙잡지 않는다(붙잡으면 방금 결제한 주문을 취소하게 됨).
- 구매자 연락처: 결제 화면의 입력칸을 없애고 회원 휴대폰 번호(`MyInfoResponse.phone`, #302에서 추가)를 넘긴다. 번호가 없는 예전 회원은 결제할 수 없다고 안내만 한다.
- 백엔드: 확정 요청이 이미 실패한 결제를 받으면(웹훅·스케줄러가 먼저 실패 처리) 실패 사유에 맞는 오류로 답하게 했다.

## 연결과 남은 작업

- 결제 확정이 타임아웃되면 결과를 모른 채 실패 문구가 뜬다. 다시 확정해 결과를 확인하는 처리는 후속 후보다.
- 결제창 닫기 API(`/fail`)와 모바일 리디렉션은 쓰지 않는다. 남은 결제 대기는 만료 스케줄러가 정리한다.
