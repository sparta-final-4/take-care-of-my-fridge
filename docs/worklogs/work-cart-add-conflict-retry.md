# 장바구니 동시 담기 충돌 처리

상태: 구현 · 작성일: 2026-11-04 · 담당: 준혁

## 목표

같은 회원의 장바구니 담기 요청이 동시에 오면 둘 다 장바구니나 항목이 없다고 보고 저장하려 해, 두 번째 저장이 유니크 제약(`uk_carts_member_id`, `uk_cart_items_cart_id_product_id`)에 막혀 500이 나던 것을 없앤다. 데이터는 제약이 지켜 주므로 깨지지 않았고, 응답만 5xx였다.

## 구현

`CartService.addItem`이 장바구니와 항목을 저장할 때 위 두 제약의 위반만 `CART_ADD_CONFLICT`(409, `CART_004`)로 바꿔 던진다. 다른 제약 위반은 원인을 가리지 않도록 그대로 던진다. 이 트랜잭션은 제약 위반으로 이미 실패한 상태라 안에서 이어서 처리하지 않고, 트랜잭션 밖의 `CartFacade.addItem`이 충돌 코드를 받으면 새 트랜잭션으로 한 번만 다시 시도한다. 두 번째 시도는 이미 생긴 장바구니와 항목을 읽어 수량을 올리는 경로로 가서 성공한다. 다시 시도해도 충돌이면 409가 그대로 나간다. 변환은 전역 예외 처리가 아니라 저장하는 서비스에서 하며, `OrderService.saveOrder`와 같은 방식이다.

같은 항목의 수량을 동시에 올릴 때 읽고 더해서 쓰는 방식 때문에 수량이 덜 늘어나는 갱신 유실은 그대로 둔다. 잠금과 버전은 넣지 않는다. 이번에 고친 것은 장바구니와 항목이 중복 생성되며 충돌하는 경우뿐이다.

API 요청·응답 형식과 DB 구조는 바뀌지 않는다. 담기에 409 오류 코드 `CART_004`가 하나 늘었다.

## 검증

`CartFacadeConcurrencyTest`가 같은 회원이 같은 상품을 5개 스레드로 동시에 담은 뒤 DB의 최종 상태를 읽어 확인한다. 장바구니가 없을 때, 장바구니만 있고 항목이 없을 때, 이미 항목이 있을 때를 다룬다. 세 경우 모두 밖으로 새어 나온 예외가 없고, 그 회원의 장바구니는 1개, 그 상품의 항목은 1개이며, 수량은 요청 수를 넘지 않는다. 앞의 두 경우는 변경 전 소스코드에서 실패하는 것을 확인했고, 변경 뒤 반복 실행에서도 통과했다. 기존 `CartServiceTest`, `CartFacadeTest`, `CartServiceTransactionTest`도 통과했다. 화면에서 담기 버튼을 연속으로 눌러 오류 없이 항목이 하나만 생기는 것도 확인했다.
