# WORK-101: 일별 상품 판매량 조회에 기준 시각 추가

상태: 검증 대기 · 작성일: 2026-10-27 · 담당: 준혁

## 목표와 완료 기준

- 판매 예측이 같은 기준 시각(`asOf`)으로 다시 조회하면 같은 판매량을 받는다.
- 기준 시각 뒤에 구매 확정된 주문은 판매량에 들어가지 않는다.
- 판매량은 확정 전에 완료된 환불을 뺀 순판매 수량이고, 상품·구매 확정일별로 합산한다.

## 근거와 범위

- 선행 작업:
  - WORK-040 구매 확정 일시와 일별 상품 판매량 조회
  - WORK-102 구매 확정 검증과 확정 수량
- 판매량은 주문 상품의 확정 수량(`confirmed_quantity`)을 합산한다. 확정 수량은 구매 확정 때 주문 수량에서 완료된 환불 수량을 뺀 값이다.
- 환불이 진행 중이면 구매 확정이 거절되고 확정 뒤에는 환불할 수 없으므로, 확정된 주문의 환불은 모두 확정 전에 끝나 있다. 그래서 확정 수량의 합이 곧 순판매 수량이고, 환불 수량을 따로 읽어 뺄 필요가 없다.
- 할인 구분(`saleType`)으로 나누지 않는다. 판매 예측이 상품·날짜로만 합산하기 때문이다.
- 판매 예측 도메인 코드는 바꾸지 않았다.

## AI 활용과 개발자 판단

- AI에 맡긴 작업: 쿼리·서비스 수정, 테스트 작성.
- 채택:
  - 기준 시각 조건을 `confirmedAt <= asOf`로 더하고 기존 상태 조건(`CONFIRMED`)은 유지했다.
  - 합산 대상을 주문 수량에서 확정 수량으로 바꿨다.
- 개발자 판단:
  - AI는 판매 예측 도메인이 주문·환불 테이블을 직접 읽는 기존 쿼리를 그대로 쓰자고 추천했다. 도메인 사이 참조 규칙을 지키려고 주문 도메인이 판매량을 제공하는 방향을 골랐다.
  - 처음에는 주문 도메인이 구매 확정 판매량만 주고 판매 예측 도메인이 환불 수량을 빼게 했다. 확정 수량이 생긴 뒤 그 합으로 순판매 수량을 주도록 바꿔, 환불을 빼는 계산이 판매 예측 쪽에 남지 않게 했다.
  - 할인 구분을 결과에서 빼기로 했다.
  - 테스트 조건(기준 시각, 확정 주문만, 합산과 기간 경계, 확정 전 환불 차감, 입력 오류)을 정했다.

## 구현 결과

- `OrderSalesService.getDailyProductSales(from, to, asOf)`: `asOf`를 받는다. `asOf`가 없으면 `from`·`to`가 없을 때와 같이 `INVALID_INPUT_VALUE`다.
- `OrderItemRepository.findDailyProductSales`:
  - `confirmedAt <= :asOf` 조건을 더했다.
  - 합산을 `sum(oi.quantity)`에서 `sum(oi.confirmedQuantity)`로 바꿨다.
  - 묶음·정렬에서 할인 구분을 뺐다.
- `DailyProductSales`: `saleType`을 빼고 `(productId, salesDate, quantity)`로 바꿨다.
- 신규 HTTP API와 ErrorCode는 없다.

## 연결과 남은 작업

- 판매 예측 도메인이 이 조회로 바꾸면, 주문·환불 테이블을 직접 읽어 환불을 빼는 판매 예측 쪽 쿼리를 정리한다.
