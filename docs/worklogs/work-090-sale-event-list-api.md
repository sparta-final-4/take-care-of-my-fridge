# WORK-090: 할인 행사 목록 조회 API

상태: 검증 대기 · 작성일: 2026-10-24 · 담당: 준혁

## 목표와 완료 기준

- 관리자가 등록된 행사를 상품 단위로 한 행씩 보고, 상태·종류·기간·상품 이름으로 찾고, 열 기준으로 정렬한다.
- 종료된 행사는 등록 당시 정가를, 예정·진행 중 행사는 상품의 현재 정가를 본다.
- 행사 상품마다 판매량(실제로 팔린 수량)을 본다.

## 근거와 범위

- 선행 작업: WORK-080 행사 등록, WORK-089 등록 당시 정가 저장. 행사 관리 화면 설계의 목록 화면에 대응한다.
- 처음 화면 설계는 특가 행사를 상품 줄이 접히는 한 줄로 보여 주지만, 같이 등록한 묶음을 목록에서 볼 필요가 없다고 판단해 **행사에 든 상품 하나가 한 행**이 되게 했다. 같이 등록할 수 있는 것은 등록 화면의 편의로 둔다.
- 판매량은 행사 상품으로 팔린 주문 상품(`order_items.sale_event_item_id`)의 수량 합이고, 결제 완료·구매 확정 주문만 센다. 취소·결제 대기 주문은 팔린 것으로 보지 않는다.
- 변경하지 않은 것: 행사 수정·종료 API, 번개 드롭 여러 개를 한 번에 등록하는 것, 상품마다 행사를 따로 만드는 등록 방식은 후속 작업이다.

## 구현 결과

- `GET /api/admin/sale-events`(ADMIN)를 추가했다. 요청: `status`, `type`, `keyword`(상품 이름, 50자 이하), 시작일(`startFrom`, `startTo`), 종료일(`endFrom`, `endTo`), `sort`, `direction`, `page`, `size`(기본 10, 최대 100).
- 날짜는 하나만 주면 그 하루만, 둘 다 주면 그 기간(양 끝 포함)이고 끝 날짜가 앞 날짜보다 빠르면 400이다.
- 정렬 기준은 상품 이름, 종류, 상태(예정, 진행 중, 종료 순서), 정가, 할인가, 할인율, 한정 수량, 남은 수량, 판매량, 시작, 종료이고 방향은 `ASC`·`DESC`다. 기준이 없으면 최신 행사부터이고, 같은 값끼리는 최신 행사가 먼저라 페이지를 넘겨도 순서가 흔들리지 않는다.
- 응답 한 행: 행사 id, 종류, 상태, 시작·종료 시각, 상품 id·이름, 정가, 할인가, 할인율, 한정 수량, 남은 수량, 판매량. 한정 수량과 남은 수량은 번개 드롭만 값이 있다.
- 응답 record는 `from(Entity)` 대신 QueryDSL이 생성자로 바로 채운다. 목록은 행사·상품·주문을 합친 값이라 엔티티 하나에서 만들 수 없고, 엔티티를 거치지 않아야 필요한 열만 읽는다.
- 판매량 계산과 정렬을 위해 행사 목록 조회가 주문 엔티티(`OrderItem`, `Order`)를 직접 읽는다. 판매량으로 정렬하려면 같은 쿼리 안에서 계산해야 하고, 주문 도메인에서 따로 가져와 합치면 페이지 단위로만 정렬되기 때문이다. 퍼사드 같은 중간 계층은 이번에는 두지 않는다.
- 새 ErrorCode는 없다.

## 검증

| 명령·시나리오 | 실행 환경·조건 | 통과/실패/미실행 | 근거 |
|---|---|---|---|
| `./gradlew clean test` 전체 | 로컬(맥), MySQL 컨테이너 | 통과 | 실패 없음 |
| 상태·종류·시작일·종료일·상품 이름 조건 | 같은 환경, DB 테스트로 실제 행을 조회 | 통과 | 날짜 하나는 그날만, 기간은 양 끝 포함 |
| 정가: 상품 정가를 바꿔도 종료 행사는 등록 당시 값 | 같은 환경 | 통과 | 예정·진행 중은 바뀐 값, 종료는 저장된 값 |
| 판매량: 결제 완료·구매 확정만 합산 | 같은 환경, 상태가 다른 주문을 만들어 조회 | 통과 | 취소·결제 대기 주문은 0으로 셈 |
| 정렬(이름, 상태, 시작·종료) | 같은 환경 | 통과 | 방향·기준 같은 값의 순서가 맞음 |
| 컨트롤러: 날짜 순서·페이지 오류 400, 일반 회원 403 | 같은 환경 | 통과 | 서비스를 부르지 않음 |

## 연결과 남은 작업

- 행사 수정 API
- 행사 종료 API
- 번개 드롭 여러 개를 한 번에 등록
- 상품마다 행사를 따로 만드는 등록 방식
- 리팩토링 고려: 위 두 가지(응답을 QueryDSL 생성자로 채우는 것, 행사 조회가 주문 엔티티를 직접 읽는 것)는 팀 백엔드 규칙과 다르다. 판매량 정렬이 필요 없어지거나 도메인 경계를 지켜야 할 때 퍼사드로 나누는 것을 고려한다.
