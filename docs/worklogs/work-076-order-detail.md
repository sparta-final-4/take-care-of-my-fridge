# WORK-076: 주문 상세 조회

상태: 검증 완료 · 작성일: 2026-10-22 · 담당: 준혁

## 목표와 완료 기준

- 로그인한 회원이 자기 주문 하나를 주문할 때 저장한 상품·가격으로 본다.
- 남의 주문과 없는 주문은 똑같이 404다.
- 결제 대기·결제 완료·취소·구매 확정 모든 상태를 보여 준다.

## 근거와 범위

- 선행 작업: WORK-069 주문 확인 조회, WORK-073 내 주문 목록 조회.
- 주문 확인 조회(`/checkout`)와 API를 나눈 상태에서 주문 상세 화면용 API를 따로 만들었다. 주문 확인은 결제 대기 주문만 돌려주고, 상세는 상태를 가리지 않는다.
- 상태로 거절하지 않는다. 목록에 보이는 주문(결제 대기 포함)은 상세도 열리고, 나중에 결제 대기 주문에 상세 입구를 달아도 API를 바꾸지 않아도 된다. 화면은 읽기만 하므로 취소된 주문을 보여 줘도 상태가 바뀔 일이 없다.
- 결제 정보(결제 수단, 결제 시도·실패 이력)는 담지 않았다. 결제 테이블에는 결제 수단이 저장되지 않고, 시도·실패 이력은 사용자 화면에 쓸 곳이 없다. 결제 도메인을 읽지 않으므로 주문에서 결제로 가는 의존도 생기지 않는다.
- 환불 표시(상품별 환불·부분 환불, 환불 금액)는 담지 않았다. 환불 상세 화면이 환불 내역을 따로 보여 주므로 주문 상세에서 같은 정보를 다시 보여 주지 않는다. 환불 테이블을 읽지 않아 주문에서 환불로 가는 의존도 없다.
- 구매 확정 시각(`confirmedAt`)은 담았다. 화면이 구매 확정일을 보여 준다. 결제 시각(`paidAt`)은 화면에 쓰지 않아 담지 않았다.

## 구현 결과

### API

`GET /api/orders/{orderId}` (`OrderController.getDetail`, `OrderQueryService.getDetail`)

| 필드 | 값 |
|---|---|
| `orderId` | 주문 ID |
| `orderNumber` | 주문번호 |
| `status` | `PENDING`, `PAID`, `CANCELLED`, `CONFIRMED` |
| `orderedAt` | 주문 시각 |
| `confirmedAt` | 구매 확정 시각. 구매 확정 전이면 `null` |
| `listPriceAmount` | 상품 금액(주문 당시 정가 × 수량의 합) |
| `discountAmount` | 할인 금액(상품 금액 − 결제 금액) |
| `payAmount` | 결제 금액(할인 후) |
| `items` | 주문 상품. 주문 확인 응답과 같은 `OrderItemResponse`(상품 ID·이름·이미지, 수량, 정가, 단가, 금액, 할인 구분) |

| 상황 | HTTP | code |
|---|---|---|
| 없는 주문, 남의 주문 | 404 | `ORDER_001` |

- 지금 상품 가격은 쓰지 않고 주문 상품에 저장한 값만 돌려준다.
- 주문 1번, 주문 상품 1번으로 쿼리 두 번이다. 주문 상품이 상품명·가격·이미지를 저장하고 있어 상품 테이블을 읽지 않고, 주문 상품 수와 상관없이 두 번이다.

### 구조

- `OrderDetailResponse` (신규): 주문 상세 화면의 응답. 주문 확인 응답(`OrderCheckoutResponse`)·목록 응답은 재사용하지 않고, 주문 상품 한 건(`OrderItemResponse`)만 같이 쓴다.
- `OrderQueryService.getDetail` (신규): `OrderReader.getOwnedOrder`로 소유를 확인하고 `OrderReader.getOrderItems`로 주문 상품을 읽는다.
- 프론트 생성 클라이언트에 이 API만 더했다. dev 스펙에 이 경로와 스키마 2개(`OrderDetailResponse`, `ApiResponseOrderDetailResponse`)만 옮긴 뒤 `pnpm oag:generate:offline`으로 생성했다. 옮긴 내용은 로컬 서버의 `/v3/api-docs`와 같다.
