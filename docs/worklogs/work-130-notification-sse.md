# WORK-130: 알림 실시간 전달(SSE)

상태: 검증 대기 · 작성일: 2026-10-31 · 담당: 준혁

## 목표와 완료 기준

- 알림이 저장되면 화면을 켜둔 회원에게 새로고침 없이 바로 반영된다.
- 서버가 여러 대여도 회원이 연결된 서버가 알림을 받는다.

## 근거와 범위

- 선행 작업: WORK-122 알림 요청 받아 저장, WORK-124 번개 드롭 알림 요청 발행, WORK-125 헤더 종 아이콘 알림.
- 알림을 만드는 쪽은 바꾸지 않는다. 지금 있는 번개 드롭 등록·시작 알림이 그대로 실시간이 된다. 특가·행사 종료 알림 신설은 범위 밖이다.
- 알림 저장은 지금처럼 Kafka 소비자가 맡는다. 저장 뒤 전달만 새로 붙는다.

## 구현 결과

- 서버 → 브라우저 SSE 연결 관리는 알림 전용이 아니라 `global/sse`의 `SseConnectionRegistry`로 뒀다. 회원마다 연결 목록을 들고, 연결 직후 신호, 30초 하트비트, 회원당 연결 한도를 맡는다. 한도를 넘으면 새 연결을 넣기 전에 가장 오래된 연결을 목록에서 먼저 빼고 닫는다. 서버 간 전달은 이 클래스가 하지 않는다.
- 연결 유지 시간(30분), 하트비트 주기(30초), 회원당 연결 한도(5개)는 `application.yml`의 `app.sse.*`로 뺐다.
- 소비자가 알림을 저장하면 Redis 채널 `notification:push`로 회원 ID만 발행한다. 알림 내용은 싣지 않아, 로그아웃 뒤 남은 연결로도 내용이 새지 않는다. 발행이 실패해도 알림은 이미 저장돼 있어 다시 던지지 않고 로그만 남긴다.
- 모든 서버가 이 채널을 구독하고, 이 서버에 그 회원의 SSE 연결이 있을 때만 `notification` 이벤트(내용 없는 `refresh` 신호)로 내보낸다.
- `GET /api/notifications/stream`: 로그인한 회원의 SSE 연결. 연결을 오래 쥐는 응답이라 `ApiResponse`로 감싸지 않는다.
- 프론트는 로그인한 동안 `EventSource`로 연결하고, 신호가 오면 안 읽은 수와 열려 있는 목록을 기존 조회 API로 다시 불러온다. 끊기면 브라우저가 다시 연결한다.
- DB 변경 없음.

## 연결과 남은 작업

- 연결 목록은 서버 메모리에 있어 서버를 재시작하면 브라우저가 다시 연결한다.
- 로그아웃해도 연결은 유지 시간(30분)까지 남는다. 그 연결로는 신호만 가고 내용은 가지 않는다.
- 미검증: 서버 여러 대에서의 전달, 화면 반영.
