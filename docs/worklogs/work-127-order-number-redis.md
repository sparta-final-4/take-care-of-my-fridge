# WORK-127: 주문번호 순번을 Redis에서 받기

상태: 검증 대기 · 작성일: 2026-10-30 · 담당: 준혁

## 목표와 완료 기준

- 서버가 여러 대여도 같은 밀리초에 만든 주문번호가 겹치지 않게 한다.
- 주문번호 형식(밀리초 시각 17자리 + 순번 3자리, 한국 시각)과 주문번호 유니크 제약은 그대로 둔다.

## 근거와 범위

- 문제
  - 지금까지 순번은 서버 메모리에서 셌다(`synchronized`, 마지막 밀리초와 순번 필드). 서버 한 대 안에서만 순서를 지킨다.
  - 서버가 두 대면 같은 밀리초에 두 서버가 모두 순번 000을 낸다. 두 번째 주문은 유니크 제약에 걸려 `ORDER_005`(잠시 후 다시 주문)를 받는다.
  - 바꾸기 전 코드에서 생성기 두 개를 같은 밀리초로 고정해 만들었더니 둘 다 `20261030143000123000`을 냈다.
- 고른 방법: 밀리초 시각을 키로 Redis에서 `INCR`해 순번을 받는다. 모든 서버가 같은 키를 세므로 서버 수와 상관없이 순번이 하나로 모인다.
- 검토한 다른 방법
  - 서버 구분 자리(밀리초 17 + 서버 1 + 순번 2): Redis가 필요 없다. 대신 서버마다 번호를 따로 설정해야 하고, 밀리초당 순번이 99로 줄어든다.
  - 겹치면 다시 만들기: 가장 단순하지만 재고 차감까지 포함한 주문 트랜잭션을 통째로 다시 해야 하고, 서버가 늘수록 더 자주 겹친다.
- 대가: 주문하기가 Redis에 기댄다. Redis가 멈추면 주문하기도 실패한다.

<details><summary>세부 정책</summary>

| 항목 | 정한 것 | 이유 |
|---|---|---|
| 키 | `order:number-seq:{밀리초 시각 17자리}` | 팀 Redis 키 규칙 `{도메인}:{목적}:{식별자}` |
| 만료 | 60초. `INCR` 결과가 1일 때 건다 | 서버끼리 시계가 어긋나도 늦은 서버가 같은 키를 이어 세려면 시계 차이보다 길어야 한다. 키는 주문이 있는 밀리초마다 하나라 메모리 부담이 없다 |
| 순번 999 초과 | `ORDER_005`로 거절 | 모든 서버의 주문을 합쳐 한 밀리초에 1000건을 넘어야 걸린다. 일어나지 않을 경우라 다음 밀리초로 넘기는 처리를 두지 않았다 |
| 시계가 뒤로 감 | 따로 막지 않음 | 만료 전에 같은 밀리초로 돌아오면 `INCR`가 이어 세서 겹치지 않는다. 만료보다 크게 돌아가 겹치면 유니크 제약이 막고 `ORDER_005`가 된다. 예전의 "마지막 시각보다 뒤로 가지 않기"는 서버 한 대 안에서만 의미가 있어 뺐다. 번호가 항상 커지는 순서는 보장하지 않지만 주문번호로 정렬하는 곳이 없다 |
| Redis 실패 | 503 `ORDER_013` "잠시 후 다시 주문해 주세요." | 연결 실패와 타임아웃(3초)을 잡아 로그를 남긴다. 주문 트랜잭션이 롤백되어 재고 차감도 되돌아간다. 생성기는 상품 행을 잠근 뒤 불리므로, Redis가 응답하지 않으면 잠금을 쥔 채 최대 3초 기다리고 같은 상품의 다른 주문도 그동안 기다린다 |

</details>

## 구현 결과

- `OrderNumberGenerator`: 서버 메모리 상태와 `synchronized`를 없애고 `StringRedisTemplate`으로 순번을 받는다. 시각을 정해 넣는 테스트용 생성자는 그대로 두었다.
- `ErrorCode`: `ORDER_NUMBER_UNAVAILABLE`(503, `ORDER_013`)를 추가했다.
- `OrderCreateService`: 주문번호가 겹치는 경우를 설명하는 주석을 지금 동작에 맞게 고쳤다.
- 화면: 프론트는 5xx에 공통 문구("서버에 문제가 발생했습니다. 잠시 후 다시 시도해 주세요.")를 보여 주므로 `ORDER_013`에도 다시 시도하라는 안내가 나간다.
- 주문 트랜잭션 테스트 3개(`OrderCreateServiceTransactionTest`, `OrderCancelServiceTransactionTest`, `OrderCreateServiceSaleTransactionTest`)는 생성기를 매번 다른 번호를 돌려주는 가짜로 바꿨다. 재고와 롤백을 보는 테스트라 번호 생성과 상관없고, Redis 컨테이너를 따로 띄우지 않는다. 주문번호 20자리 확인은 생성기 테스트로 옮겼다.

<details><summary>테스트 조건 (`OrderNumberGeneratorTest`)</summary>

- 생성기 두 개(서버 두 대 역할)가 같은 Redis를 쓰고 같은 밀리초로 고정된 채 동시에 500개씩 만들면, 1000개가 모두 다르고 순번 000~999가 빠짐없이 채워진다. Redis의 순번 키 값도 1000이다.
- 번호는 한국 시각 17자리와 순번 3자리(UTC 자정 → `20261021090000000000`)이고, 순번 키의 만료 시간이 0초보다 크고 60초 이하다.
- 같은 밀리초의 1001번째 요청은 `ORDER_005`로 거절한다.
- 연결할 수 없는 Redis를 쓰면 `ORDER_013`으로 거절한다. 가짜 객체가 아니라 실제 연결 실패다.

</details>
