# WORK-120: 구매 확정 이벤트 발행

상태: 검증 대기 · 작성일: 2026-10-30 · 담당: 준혁

## 목표와 완료 기준

- 주문이 결제 완료에서 구매 확정으로 바뀌면 `purchase-confirmed` 토픽으로 구매 확정 이벤트를 보낸다. 냉장고 도메인이 이 메시지로 구매한 상품을 냉장고에 넣는다.
- 이미 확정된 주문을 다시 확정하거나, 확정이 거절되면 보내지 않는다.
- 같은 주문을 동시에 여러 번 확정해도 한 번만 보낸다.

## 근거와 범위

- 발행 시점
  - 구매 확정이 커밋된 뒤(`@TransactionalEventListener(AFTER_COMMIT)`)에 보낸다. 트랜잭션 안에서 보내면 확정이 롤백돼도 메시지는 이미 나가 있다.
  - 발행이 실패해도 확정은 되돌리지 않는다. 확정은 사용자가 실제로 한 일이라, 주문 ID를 에러 로그로 남긴다.
  - 자동 구매 확정도 주문마다 같은 `OrderConfirmService.confirm`을 따로 트랜잭션으로 부르므로 따로 손대지 않았다.
- 메시지
  - 주문 하나에 메시지 하나이고, 주문 상품 목록을 함께 싣는다. 확정 뒤에는 환불이 없어 값이 바뀌지 않으므로, 받는 쪽이 주문 도메인을 다시 조회하지 않아도 된다.
  - 확정 수량이 0인 주문 상품(완료된 환불로 전부 돌려준 상품)은 싣지 않는다.
  - 상품이 모두 환불된 주문도 결제 완료로 남아 있다가 확정되므로, 상품 목록이 빈 메시지가 나간다. 구매 확정마다 한 번 나간다는 규칙을 지켜, 이 토픽을 받는 쪽이 모든 확정을 볼 수 있게 했다.
  - 키는 주문 ID다. 같은 주문의 메시지는 같은 파티션으로 간다.
- 범위는 발행까지다. 입고, 중복 메시지 거르기, 입고 알림 여부는 받는 쪽이 정한다.

<details><summary>메시지 형식</summary>

```json
{
  "orderId": 100,
  "memberId": 7,
  "confirmedAt": "2026-10-30T14:30:05",
  "items": [
    { "orderItemId": 11, "productId": 3, "productName": "대파", "confirmedQuantity": 2 }
  ]
}
```

- `confirmedQuantity`는 상품 개수다. 재료 양으로 바꾸는 것은 받는 쪽이 한다.
- `items`는 빈 목록일 수 있다. 상품이 모두 환불된 주문이 확정된 경우다.
- 필드를 더하는 것은 받는 쪽을 깨지 않는다. Kafka 메시지 변환이 모르는 필드를 무시한다. 이름을 바꾸거나 빼면 받는 쪽에서 null이 되므로 받는 쪽과 맞춘 뒤 바꾼다.

</details>

## 구현 결과

- `OrderConfirmedEvent`(새로 만듦): 주문과 확정 수량이 남은 주문 상품으로 메시지를 만든다.
- `OrderConfirmedEventListener`(새로 만듦): 커밋 뒤 `KafkaTopics.PURCHASE_CONFIRMED`로 보낸다. 보내는 중 바로 난 예외와 전송 결과로 돌아온 실패 모두 주문 ID와 함께 로그로 남긴다.
- `OrderConfirmService.confirm`: 상태를 구매 확정으로 바꾸고 확정 수량을 저장한 다음 이벤트를 발행한다. 이미 확정된 주문과 환불 진행 중인 주문은 그 전에 빠진다.
- 클래스 이름은 주문 도메인 코드(`OrderConfirmService`, `Order.confirm`)에 맞추고, 토픽 이름은 받는 쪽과 맞춘 `purchase-confirmed`를 그대로 쓴다.

  - `purchase-confirmed` 토픽에 주문 ID를 키로 도착하고, JSON 필드 이름과 값이 위 메시지 형식과 같다.
