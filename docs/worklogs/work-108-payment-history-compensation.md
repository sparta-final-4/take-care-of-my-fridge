# WORK-108: 결제 이력과 보상 취소 재시도

상태: 완료 · 작성일: 2026-10-26 · 담당: 결제·환불

## 목표와 완료 기준

- 결제 한 건에 일어난 일(생성·승인·실패·PG 취소)을 누가 언제 왜 했는지 이력으로 남긴다.
- 받지 않기로 한 결제가 PG에서 결제됐는데 보상 취소가 실패하면, 웹훅 재전송이 끝났거나 서버가 꺼져 있었어도 다시 취소한다.

## 근거와 범위

- PR: #277(결제 이력, 10/26), #278(보상 취소 이력과 재시도 스케줄러, 10/26).
- 결제 상태(`payments.status`)는 결제 대기·결제 완료·실패만 갖는다. 환불·보상 취소로 돈이 돌아간 사실을 결제 상태에 넣지 않고 이력에만 남긴다(결제·환불 분리).
- 이전에는 보상 취소 실패를 웹훅 재전송에만 기댔고, 확정 요청에서 삼킨 취소 실패는 다시 시도할 근거가 남지 않았다.

## 구현 결과

- `payment_histories` 테이블과 `PaymentHistory` 엔티티: 사건 종류, 금액, 누적 취소 금액, 환불 ID, PG 취소 ID, 주체(`USER`·`WEBHOOK`·`SCHEDULER`), 사유. 추가만 하고 고치지 않는다.
- `PaymentHistoryRecorder`: 이력을 남기는 곳을 한 곳으로 모았다. 결제 상태 변경과 같은 트랜잭션에서 불러 함께 저장·롤백된다. 사유가 길면 255자에서 잘라 저장 실패로 상태 변경까지 롤백되는 일을 막는다.
- 결제 상태를 바꾸는 경로마다 호출 주체를 넘기도록 `PaymentCommandService`·`PaymentFacade` 시그니처를 바꿨다. `FailReason`에 이력 사유용 설명을 더했다.
- 보상 취소
  - 취소 전에 "PG에서 결제됨"(`PAID`, 받지 않은 결제)을, 성공하면 전액 취소(`CANCELLED`)와 PG 취소 ID를 남긴다. 웹훅 재전송으로 여러 번 불려도 한 번씩만 남긴다.
  - 실패 결제인데 이력에 `PAID`만 있고 `CANCELLED`가 없으면 보상 취소가 끝나지 않은 결제다.
- `PaymentTimeoutScheduler.retryCompensations`: 5분마다 위 결제를 id 커서로 100건씩 찾아 PG를 조회한다. 아직 결제 상태면 다시 취소하고, 이미 취소됐으면 기록만 남겨 대상에서 뺀다. 상태가 예상과 다르면 로그만 남긴다.
- 웹훅에서도 PG 취소 + 우리 실패 결제를 보면 기록만 남긴다(콘솔 등 다른 경로로 취소된 경우).
- 환불 쪽은 환불이 완료될 때 `recordCancellation`만 부른다. 누적 취소 금액이 결제 금액에 닿으면 전액 취소, 아니면 부분 취소로 남는다.
