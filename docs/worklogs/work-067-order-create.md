# WORK-067: 주문하기

상태: 검증 완료 · 작성일: 2026-10-20 · 담당: 준혁

## 목표와 완료 기준

- 장바구니에서 고른 항목으로 결제 대기(`PENDING`) 주문을 만들고, 그 순간 재고를 뺀다.
- 여러 회원이 동시에 주문해도 재고보다 많이 팔리지 않는다.
- 같은 주문하기 요청이 여러 번 와도(따닥, 재전송) 주문은 하나만 생긴다. 새로 누른 주문은 같은 상품이어도 만들어진다. 한 회원이 여러 건 주문할 수 있다.

## 근거와 범위

- 선행 작업: WORK-039 장바구니 담기, WORK-041 장바구니 조회, WORK-066 장바구니 상품 연동.
- 주문하기 전체를 트랜잭션 하나로 처리한다. 하나라도 실패하면 앞서 뺀 재고까지 롤백한다. 외부 호출이 없어 퍼사드를 두지 않았다.
- 중복 요청은 `Idempotency-Key` 헤더로 구분한다.
- 주문 서비스는 기능별로 나눈다. 이번에는 주문하기만 `OrderCreateService`에 둔다.
- 장바구니 항목은 지우지 않는다. 결제 완료 때 지운다.
- 상품 도메인 코드에 재고 차감 메서드(`Product.decreaseStock`)와 잠금 조회(`ProductRepository.findAllByIdInForUpdate`)를 추가했다.
- 할인가·할인 구분·번개 드롭 한도는 할인 행사 조회가 없어 이번 범위에서 뺐다. 단가는 정가, 할인 구분은 `NONE`이다.
- 주문 취소, 5분 만료, 결제하기는 이번 범위가 아니다.

## 구현 결과

- `POST /api/orders` (`OrderController`, `OrderCreateService.createOrder`)
  - 헤더: `Idempotency-Key`(필수, 64자 이하). 없거나 길면 400 `INVALID_INPUT_VALUE`.
  - 요청: `cartItemIds`(1개 이상 50개 이하).
  - 처리 순서: 회원의 장바구니 행 잠금 → 고른 장바구니 항목 읽기 → 같은 멱등 키 주문이 있으면 그 주문을 돌려줌(장바구니 항목이 모두 남아 있으면 상품·수량을 비교해 다르면 거절) → 고른 장바구니 항목이 모두 내 것인지 확인 → 상품 행을 ID 순으로 잠그고 읽기 → 판매 중지 확인 → 재고 확인·차감 → 주문·주문 상품 저장.
  - 응답: 새 주문은 201, 같은 멱등 키로 이미 만든 주문은 200. 둘 다 주문 상세 모양(`orderId`, `orderNumber`, `status`, `orderedAt`, `listPriceAmount`, `discountAmount`, `payAmount`, `items[]`). `items[]`는 `productId`, `productName`, `productImageUrl`, `quantity`, `listPrice`, `unitPrice`, `lineAmount`, `saleType`.
- 재고 차감: `findAllByIdInForUpdate`(`SELECT … FOR UPDATE … ORDER BY id`)로 상품을 잠그고 읽은 뒤 `Product.decreaseStock`으로 빼고(수량이 0 이하면 400 `INVALID_INPUT_VALUE`로 재고가 늘어나는 것을 막고, 재고가 모자라면 품절·재고 부족 문구와 상품명을 담아 409 `INSUFFICIENT_STOCK`. 재고 규칙과 문구를 엔티티 한 곳에 둔다), 저장은 더티 체킹에 맡긴다. 한 문장에서 ID 순으로 잠그므로 주문끼리 잠금 순서가 엇갈리지 않는다.
- 중복 요청: 주문에 멱등 키를 저장한다(`orders.idempotency_key`, `(member_id, idempotency_key)` 유니크). 장바구니 행을 `findByMemberIdForUpdate`로 잠가 같은 회원의 주문하기를 하나씩 순서대로 처리한 뒤 같은 키의 주문을 찾으므로, 같은 키로 동시에 온 요청도 모두 같은 주문을 받는다. 이 잠금은 트랜잭션의 첫 조회여야 한다. 유니크 제약은 잠금이 빠졌을 때 주문이 두 번 생기는 것을 막는 마지막 장치다. 같은 키 확인은 장바구니 항목 검증보다 먼저 해서, 처음 주문 뒤 장바구니 항목이 지워져도(결제 완료, 사용자 삭제) 재전송에는 처음 주문을 돌려준다. 같은 키인데 고른 상품·수량이 처음 주문과 다르면 409 `ORDER_IDEMPOTENCY_KEY_REUSED`로 거절한다. 처음 주문의 주문 상품과 비교하므로 따로 저장하는 값은 없고, 장바구니 항목이 일부 사라져 비교할 수 없으면 처음 주문을 그대로 돌려준다.
- 주문번호: `OrderNumberGenerator`가 밀리초 시각 17자리와 같은 밀리초 안의 순번 3자리로 20자리 숫자를 만든다. DB를 조회하지 않는다. 서버 1대 기준이다. 시각은 서버 시간대와 관계없이 `Asia/Seoul`로 찍는다. 시계가 뒤로 가면 마지막 시각에 머물고, 그동안 순번이 999를 넘으면 다음 밀리초로 넘겨 20자리를 지킨다.
- 주문 상품에 주문 당시 상품명·이미지·정가·단가를 복사한다. `order_items.product_image_url`(NULL 허용) 컬럼을 추가했다.
- 신규 오류 코드
  - `ORDER_NUMBER_CONFLICT`(409, `ORDER_005`, "잠시 후 다시 주문해 주세요."). 주문번호 유니크(`uk_orders_order_number`)나 멱등 키 유니크(`uk_orders_member_id_idempotency_key`) 위반일 때만 난다. 시계가 뒤로 간 채 재시작했을 때처럼 드문 경우다. 그 밖의 제약 위반은 원인을 가리지 않도록 그대로 던지고, 모든 경우 원인 예외를 경고 로그로 남긴다.
  - `ORDER_IDEMPOTENCY_KEY_REUSED`(409, `ORDER_006`, "다른 주문 요청에 이미 쓴 Idempotency-Key입니다.").
- 그 밖의 오류: `cartItemIds`가 비었거나 50개를 넘으면 400 `INVALID_INPUT_VALUE`, 내 장바구니 항목이 아니면 404 `CART_ITEM_NOT_FOUND`, 장바구니 항목의 상품이 없으면 404 `PRODUCT_NOT_FOUND`, 판매 중지 409 `PRODUCT_NOT_ON_SALE`, 재고 부족 409 `INSUFFICIENT_STOCK`(메시지 "재고 부족 · 상품명", 재고 0이면 "품절 · 상품명").
- 테스트
  - `OrderCreateServiceTransactionTest`(Testcontainers MySQL, 커밋된 DB 상태로 확인): 주문 성공 시 재고 감소·주문 저장·장바구니 유지, 두 번째 상품 재고 부족 시 첫 상품 재고까지 롤백, 재고 0 품절, 판매 중지, 남의 장바구니 항목, 상품이 없어진 장바구니 항목, 같은 멱등 키 재요청 시 처음 주문 반환·재고 한 번만 차감, 주문 뒤 장바구니 항목을 지운 다음 같은 키 재요청 시 처음 주문 반환, 같은 키·다른 상품 거절·처음 주문과 재고 유지, 키가 다르면 같은 상품도 새 주문, 다른 회원은 같은 키로도 각자 주문, 키 없음·64자 초과 거절, 장바구니 수량이 음수인 항목 거절·재고와 주문 그대로, 재고 5개에 20명 동시 주문 시 정확히 5건만 성공·재고 0, 같은 키 동시 5회 주문 시 주문 1건·모두 같은 주문 반환, 담은 순서가 엇갈린 주문 20건 동시 실행 시 데드락 없이 모두 성공·재고 정합성 확인.
  - `OrderCreateServiceConstraintTest`(주문번호 생성기를 대신해 같은 번호를 두 번 냄): 두 번째 주문이 409 `ORDER_NUMBER_CONFLICT`로 거절되고 주문 1건, 재고는 한 번만 차감.
  - `OrderControllerTest`: 새 주문 201, 같은 키 200, 키 없음 400, 빈 `cartItemIds` 400, `cartItemIds` 51개 400.
  - `OrderNumberGeneratorTest`: 20자리 형식, 연속 생성 시 증가, 여러 스레드 동시 생성 시 중복 없음, 같은 밀리초 1001번째에서 다음 밀리초로 넘어감, 시계가 뒤로 가도 증가, UTC 자정이 한국 시각 09시로 찍힘.
  - `ProductTest`: 재고 차감, 재고보다 많이 빼면 거절하고 재고 유지, 0 이하 수량 거절하고 재고 유지, 품절·재고 부족 문구에 상품명 포함.

## 연결과 남은 작업

- 주문 취소(결제하기 전에만 가능)와 5분 만료가 없어, 결제하기 전에 나간 주문이 재고를 잡은 채로 남는다. 다음 작업으로 취소(재고 되돌리기 포함)와 만료를 만든다.
- 결제 실패 시 결제 도메인이 주문을 취소하지만 재고는 되돌리지 않는다. 주문 도메인이 재고 되돌리기 메서드를 만들면 결제 도메인이 그 메서드를 부른다(결제 코드에 TODO).
- 할인가·할인 구분·번개 드롭 한도는 할인 행사 조회를 만든 뒤 붙인다(서비스에 TODO).
- 주문 상세 조회(`GET /api/orders/{orderId}`)는 다음 작업이다. 이번 응답 record를 그대로 쓴다.
- 서버를 2대 이상으로 늘리면 주문번호 방식(서버 구분 자리 추가 또는 DB ID 기반)을 바꾼다.
- 주문 API 명세는 TODO가 정리된 뒤 묶어서 갱신한다.
- 프론트(주문 화면)
  - 장바구니 화면의 주문하기 버튼을 이 API에 연결한다. 고른 장바구니 항목 번호를 `cartItemIds`로 보낸다.
  - `Idempotency-Key`는 주문 시도 하나에 하나를 만든다. 같은 시도의 재전송·따닥 클릭에는 같은 값을 쓰고, 응답을 받은 뒤 다음 시도에는 새 값을 쓴다. 버튼은 누른 직후 비활성화한다.
  - 201과 200은 같은 주문 응답이므로 둘 다 주문 확인 화면(02)으로 넘어간다.
  - 409는 메시지를 알림으로 띄운다. 재고 부족·품절은 "재고 부족 · 상품명" 형식, `ORDER_006`은 화면 버그 신호, `ORDER_005`는 다시 주문 안내다.
  - 주문 확인 화면은 이번 응답으로 그린다. 상품 이미지(`productImageUrl`)가 null이면 빈 이미지를 보여 준다. 새로고침·재진입은 주문 상세 조회 API가 생긴 뒤 붙인다.
