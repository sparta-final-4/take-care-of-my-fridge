# 지금 뜨는 할인 조회 캐시

상태: 구현 · 작성일: 2026-11-05 · 담당: 준혁

## 목표

메인 화면 지금 뜨는 할인(`GET /api/sales/popular`)이 요청마다 같은 일을 반복하던 것을 줄인다.

- 요청마다 최근 7일 검색 클릭 전체를 상품별로 묶어 센다. 결과는 모든 사용자에게 같다.
- 요청 1건이 트랜잭션 5개로 나뉘어 SQL 28문을 보낸다. 데이터 조회는 3문(진행 중 할인, 상품, 검색 클릭 집계)이고 나머지는 트랜잭션 시작·종료 문장이다.
- 메인 화면 부하 측정에서 이 요청이 처음부터 다른 요청보다 느렸다.

## 구현

**트랜잭션 정리**

- `PopularSaleService`의 `@Transactional`을 뗐다. DB를 읽지 않고 넘겨받은 값으로 계산만 하는데, 클래스에 붙어 있어 `clickFrom`과 `rank`가 SQL 없는 트랜잭션을 하나씩 열고 있었다.
- 진행 중 할인이 없으면 상품과 검색 클릭을 읽지 않고 빈 목록을 돌려준다.

**캐시**

- `SaleEventFacade.getPopularSales`에 `@Cacheable`을 붙였다. 캐시 이름은 `sale:popular`, 키는 `all`, TTL은 10초다.
- 비우는 시점은 두지 않고 TTL로만 바꾼다. 번개 드롭은 시작 시각이 되면 보이므로, 등록할 때 비워도 그 시각을 맞출 수 없다.
- 대가로 품절, 할인 종료, 번개 드롭 남은 수량("N/M개 남음")이 메인 화면에 최대 10초 늦게 반영된다. 상품 상세와 주문은 캐시를 거치지 않고 판매가와 남은 수량을 실시간으로 확인한다.
- TTL을 짧게 둔 이유: 부하가 줄어드는 것은 요청마다 하던 집계를 TTL마다 한 번으로 바꾼 데서 오므로, TTL을 더 길게 둬도 DB 부하는 거의 줄지 않는다. 반면 번개 드롭 남은 수량은 몰릴 때 몇 초 단위로 바뀐다.
- 진행 중 할인이 없는 빈 결과도 캐시한다. 할인이 없는 상태도 정상이라, 빼면 그동안 요청마다 다시 계산한다.
- 목록은 `PopularSaleList` record로 감싸 캐시한다. 컨트롤러는 `.sales()`로 꺼내므로 API 응답 형식은 바뀌지 않는다.
- `SaleResponse.endsAt`에 `@JsonFormat(without = ADJUST_DATES_TO_CONTEXT_TIME_ZONE)`을 붙였다. Redis에서 꺼낼 때 Jackson이 `OffsetDateTime`을 UTC로 바꿔, 캐시 적중 응답만 `+09:00` 대신 `Z`로 나가던 것을 막는다. 응답을 만들 때는 영향이 없다.

**동시 미스**

- `@Cacheable(sync = true)`는 넣지 않았다. 팀 캐시 설정의 Redis 캐시는 잠금을 쓰지 않아서 `sync`를 붙여도 동시 미스를 막지 못한다.
- 그래서 키가 만료되는 순간과 캐시 미스 직후 값이 Redis에 들어가기 전 잠깐 동안 들어온 요청은 집계를 한 번 더 한다. 캐시 쓰기가 비동기라 그 사이에 틈이 생긴다.

DB 구조는 바뀌지 않는다.

## 검증

**요청 1건의 SQL 수**

로컬 부하 테스트 환경에서 MySQL 일반 로그로 셌다. 앱은 최신 `dev`에 이번 변경을 얹어 빌드했다.

| 경우 | SQL | 트랜잭션 |
|---|---|---|
| 변경 전 | 28문 | 5개 |
| 트랜잭션 정리 후 | 18문 | 3개 |
| 캐시 적용 후, 캐시 미스 | 18문 | 3개 |
| 캐시 적용 후, 캐시 적중 | 0문 | 0개 |

같은 환경에서 캐시를 비운 뒤 두 번 불러 캐시 미스와 적중의 응답이 같은지 비교했고, `endsAt`까지 같았다.

**테스트**

`SaleEventFacadeCacheIntegrationTest`가 실제 Redis 컨테이너에 넣고 꺼내 확인한다. 진행 중 할인, 상품, 검색 클릭은 목으로 둔다.

- 두 번째 호출은 진행 중 할인, 상품, 검색 클릭을 다시 읽지 않는다.
- 캐시에서 꺼낸 결과는 첫 호출과 같고, 종료 시각이 `+09:00`으로 남는다.
- 진행 중 할인이 없는 빈 결과도 캐시되어, 두 번째 호출은 진행 중 할인을 다시 읽지 않는다.

`endsAt` 표시를 뺀 소스코드에서는 두 번째 테스트가 실패하는 것을 확인했다.

Redis 캐시는 넣기와 비우기를 비동기로 실행해서, 테스트가 실행할 때마다 다른 결과를 냈다. 그래서 테스트를 두 군데 고쳤고, 반복 실행에서 통과했다.

- 테스트 사이에 비울 때는 바로 지우는 `invalidate()`를 쓴다.
- 첫 호출 뒤에는 값이 Redis에 들어갈 때까지 기다린 다음 두 번째로 호출한다.

기존 `SaleControllerTest`와 `PopularSaleServiceTest`도 통과했다.
