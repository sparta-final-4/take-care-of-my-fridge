# WORK-078: 구매 확정

상태: 검증 완료 · 작성일: 2026-10-23 · 담당: 준혁

## 목표와 완료 기준

- 로그인한 회원이 자기 결제 완료 주문을 구매 확정으로 바꾼다. 구매 확정 뒤에는 환불할 수 없다.
- 같은 주문의 구매 확정이 여러 번 오거나 동시에 와도 결과는 구매 확정 하나다.
- 남의 주문과 없는 주문은 똑같이 404다.

## 근거와 범위

- 선행 작업: WORK-071 주문 취소, WORK-076 주문 상세 조회.
- 결제 완료(`PAID`) 주문만 확정한다. 배송 개념이 없어 결제 뒤 기간 같은 조건은 두지 않는다.
- 이미 구매 확정된 주문에는 상태를 건드리지 않고 같은 200 응답을 준다. 버튼 연타나, 화면을 띄워 둔 사이 확정이 먼저 된 경우에도 사용자가 원한 결과(구매 확정)는 같기 때문이다. 이미 취소된 주문에 같은 응답을 주는 주문 취소와 같은 방식이다.
- 주문 행을 잠그고 상태를 확인한다. 같은 주문의 구매 확정이 동시에 와도 하나씩 순서대로 처리되고, 결제 완료에서 구매 확정으로 바꾼 요청만 확정 시각을 남긴다.
- 환불 신청(`RefundCommandService.request`)도 같은 주문 행을 잠그고 구매 확정 주문을 `REFUND_010`으로 거절한다. 구매 확정과 환불 신청이 동시에 와도 하나씩 순서대로 처리된다.
- 환불이 진행 중(`REQUESTED`)인 주문의 구매 확정은 지금 막지 않는다. 환불 처리(PG 취소)가 붙을 때 환불 도메인과 함께 정한다. 지금은 환불 API가 없어 이 상태가 생기지 않는다.
- 자동 구매 확정 스케줄러(결제 완료 후 정한 시간이 지난 주문, 시간은 미정)와 냉장고로 가는 구매 확정 이벤트는 다음 작업으로 둔다. 스케줄러는 이 작업의 확정 메서드를 부르기만 하면 되고, 이벤트는 아직 받는 쪽이 없다.

## 구현 결과

### API

`PATCH /api/orders/{orderId}/confirm` (`OrderController.confirmOrder`, `OrderConfirmService.confirm`). 요청 본문은 없다.

응답 200: `{ orderId, status: "CONFIRMED" }` (`OrderConfirmResponse`, 주문 취소 응답과 같은 모양). 확정 시각은 주문 상세 조회의 `confirmedAt`으로 본다.

| 상황 | HTTP | code |
|---|---|---|
| 결제 완료 주문 | 200 | 구매 확정으로 바꾸고 확정 시각을 남긴다 |
| 이미 구매 확정된 주문 | 200 | 같은 응답, 상태와 확정 시각은 그대로 |
| 결제 대기 주문 | 409 | `ORDER_009` (신규, `ORDER_NOT_PAID`) |
| 취소된 주문 | 409 | `ORDER_008` |
| 없는 주문, 남의 주문 | 404 | `ORDER_001` |

### 구조

- `Order.confirm()`: 가드절로 취소된 주문은 `ORDER_CANCELLED`, 그 밖에 결제 완료가 아닌 주문은 `ORDER_NOT_PAID`로 거절한다. 전에는 둘 다 400 `INVALID_ORDER_STATUS`였다. `isConfirmed()`를 더했다.
- `OrderConfirmService` (신규): `OrderReader.getOwnedOrderForUpdate`로 잠가 찾고, 이미 구매 확정이면 같은 응답, 아니면 `confirm()`을 부른다.
- `ErrorCode.ORDER_NOT_PAID` (`ORDER_009`, 409, "결제 완료된 주문만 구매 확정할 수 있습니다.").
