# WORK-113: 환불 실패 대처, 요청 상태 환불 정리, 취소 웹훅 연동

상태: 완료 · 작성일: 2026-10-26 · 담당: 결제·환불

## 목표와 완료 기준

- PG가 환불을 거절하면 실패로 남기고, 사용자는 같은 수량을 다시 신청할 수 있다.
- PG 결과를 모르는 환불(타임아웃·5xx)도 결국 완료 또는 실패로 정리된다.
- PortOne 콘솔에서 직접 취소한 것처럼 우리 환불 기록에 없는 PG 취소도 결제 이력에 남는다.

## 근거와 범위

- PR: #280(환불 실패 대처와 정리 스케줄러), #281(취소 웹훅으로 환불을 PG와 맞추기). 모두 10/26.
- 한 결제에 PG 취소가 한 건씩만 진행되도록 같은 주문의 진행 중 환불을 한 건으로 제한한다. 그래야 "PG 누적 취소 금액 − 우리가 기록한 취소 금액"이 진행 중 환불 금액과 같은지로 결과를 판단할 수 있다.
- PG에서 돈이 돌아간 환불은 실패로 바꾸지 않는다. 결과를 모르면 요청 상태로 두고 나중에 PG로 확인한다.

## 구현 결과

- `RefundFacade.request`
  - PG 거절(4xx → `PG_CANCEL_REJECTED`): 실패로 바꾸고 PG 오류 원문을 `fail_reason`에 남긴 뒤 `REFUND_012`.
  - 결과 모름: 바로 PG를 조회해 판단하고, 확정하지 못하면 요청 상태(201, `REQUESTED`)로 응답한다.
  - PG 취소 뒤 완료 처리가 실패: 실패로 바꾸지 않고 요청 상태로 응답한다. PG 취소 ID는 로그에 남긴다.
- 같은 주문에 요청 상태 환불이 있으면 새 신청을 거절한다(`REFUND_007`).
- PG 취소 멱등 키를 환불 ID로 만든 이름 기반 UUID로 바꿨다. PortOne은 UUID 형식만 받고, 같은 환불은 몇 번 요청해도 한 번만 취소된다.
- `RefundFacade.syncWithPg`: PG를 먼저 조회한 뒤 우리 기록을 읽는다(그 사이 새로 시작된 환불을 모르는 취소로 오해하지 않게).
  - 새 취소 금액 = 진행 중 환불 금액: 아직 기록하지 않은 같은 금액의 PG 취소 ID로 완료.
  - 새 취소 금액 0: 기준 시각보다 먼저 신청된 환불만 실패로 바꾼다.
  - 진행 중 환불 없이 취소 금액이 늘었음: 환불 기록 없는 취소로 결제 이력에만 남기고 재고는 건드리지 않는다.
  - 그 밖(금액이 맞지 않음, 기록이 더 큼): 바꾸지 않고 수동 확인 로그.
- `RefundReconcileScheduler`: 5분마다 10분 넘게 요청 상태인 환불이 있는 결제를 같은 기준 시각으로 PG와 맞춘다. 한 결제가 실패해도 나머지는 계속한다.
- 환불이 완료되면 결제 이력에 부분 취소(`PARTIAL_CANCELLED`)를, 누적 취소가 결제 금액에 닿으면 전액 취소(`CANCELLED`)를 남긴다.
- `PortOneClient`: 4xx를 `PG_CANCEL_REJECTED`(`PAYMENT_009`)로 바꾸고, 조회 응답에 PG 취소 건 목록을 더했다.
- 웹훅(#281): `Transaction.PartialCancelled`를 처리 대상에 더하고, 취소·부분 취소 웹훅이면 `syncWithPg`를 부른다. API로 이미 완료한 환불의 웹훅은 바꿀 것이 없어 `IGNORED`.

## 연결과 남은 작업

- 타임아웃으로 다시 보낸 취소 요청에 4xx가 오면, 앞선 요청이 이미 취소됐을 수도 있는데 실패로 처리된다. 결과 모름으로 보는 처리는 후속 후보다.
- PG 누적 취소 금액이 진행 중 환불과 맞지 않으면 그 주문은 요청 상태 환불이 남아 새 신청을 받지 못한다. 수동 확인이 필요하다.
