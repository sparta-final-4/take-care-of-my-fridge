# 상담 후보 ES 연결과 분류·키워드 보완

상태: 검증 대기 · 작성일: 2026-11-06 · 담당: zcookiez

브랜치 `feat/chat-candidates-es`에서 한 작업이다. 커밋은 로컬에만 있고 push·PR은 하지 않았다.

1. 상담 후보 모으기를 ES 후보 검색으로 연결
2. 분류 단어 서버 확인
3. 후속 의도 프롬프트 보완
4. "탕짜면" 관련 보완: 키워드 늘리기, 벡터 1번, 요리 이름 채우기, 키워드별 고르기, 다른 제안 표시
5. 재료로 맞기를 키워드 통째로만 인정

## 목표와 완료 기준
- 사용자 문제:
  - AI 상담 추천 후보를 냉장고·선택 재료로 레시피를 역조회해서 모았다. 그래서 "디저트 추천해줘"처럼 분류만 말하면 냉장고와 겹치지 않는 디저트가 후보에 들지 못했다. 회원 5번 기준 후보는 1,281건이었다.
  - 같은 상담(세션 54)에서 "디저트 추천해줘"를 세 번 보냈더니 세 번 다 결과가 달랐다. 그중 두 번은 디저트가 아니었다.
  - "탕짜면 먹고 싶어"에서 냉장고 기준 추천이 나왔고, 비슷한 요리가 한쪽(볶음면)으로 쏠리거나 이유가 엉뚱하게 나왔다.
- 확인 가능한 완료 조건:
  - 후보 모으기만 ES로 바꾸고, 정렬·카드 고르기·카드 이유 규칙은 유지한다.
  - 앞에 무엇을 추천했든 "디저트 추천해줘", "다른 디저트 추천해줘", "다른 거 추천해줘"(앞이 디저트일 때) 모두 디저트가 나온다.
  - 레시피에 없을 법한 요리 이름이면 비슷한 요리로 늘리고, "○○ 레시피는 없어서…" 안내가 붙는다.
  - 카드는 키워드마다 고르게 고른다.

## 근거와 범위
- 레시피 담당 작업: `856e57ca`(#590, 인덱스 필드), `f5818aea`(#591, `RecipeCandidateSearchService`)
- 변경 영역: chat 도메인만 바꿨다. search·recipe 코드는 바꾸지 않았다.
  - `RecipeCandidateFacade`, `RecipeCandidateScorer`, `RecipeCandidateConditions`(신규)
  - `ChatIntentFacade`, `CategoryWordChecker`(신규), `TasteWordChecker`
  - `ChatRecommendationFacade`, `RecommendationPicker`, `RecommendationReasonWriter`, `KeywordMatchClassifier`
  - `RecipeQuery`, `IntentResult`
  - 프롬프트 `chat-intent.txt`, `chat-intent-followup.txt`
- 정한 정책:
  - 피할 맛은 3개 미만이면 다시 채운다.
  - ES 장애 때나 ES를 쓰지 않는 설정이면 DB 경로로 모은다.
  - 직전 카드는 ES에서 빼지 않고 지금처럼 `withoutPrevious`가 뺀다.
  - 분류·키워드가 있으면 요청 조건만 넣은 검색을 한 번 더 해서 합친다.
  - 벡터는 키워드로 맞은 게 없을 때만, 한 번만 쓴다.

## AI 활용과 개발자 판단
- AI에 맡긴 작업:
  - 레시피 담당 작업 조사와 연결 방법 제안
  - 구현·단위 테스트
  - dev DB(MySQL) + 로컬 ES 비교 실행
  - 세션 54 원인 분석 (dev DB 메시지·카드, 로컬 Redis 직전 조건)
- 계획에 없이 추가한 변경 (따로 커밋):
  - 말한 분류가 맞은 레시피도 1차 후보로 둔다(`9043537b`). 비교 실행에서 ES가 디저트 68건을 후보로 가져와도, 보유 비율 기준 미만이라 2차로 밀려 상위 10개에 들지 못했다.
- 사용자 요청과 다르게 구현한 것:
  - 요리 이름 채우기는 `ChatRecommendationFacade`에서 한다. 사용자 말 원문과 카드 이유·안내가 이 단계에 함께 있기 때문이다.
  - 레시피 이름 확인은 정렬된 후보 10개 이름으로 한다. 이름이 맞은 레시피는 요청 일치로 앞에 오므로 결과는 같다.
- 보류: 매울 수 있음(MILD)에 "고추" 넣기, DB 대체 경로 삭제, 레시피 담당 코드 수정

## 구현 결과

### 1. ES 후보 검색 연결
- `c59049ea` `RecipeCandidateScorer.rank`가 받은 후보 id를 그대로 정렬한다. 냉장고와 안 겹치는 후보도 다시 거르지 않는다.
- `2ff65be9` 후보를 ES 후보 검색으로 모은다.
  - `RecipeCandidateConditions`가 RecipeQuery를 검색 조건으로 바꾼다.
    - 같은 종류 묶음은 펼쳐서 넘긴다.
    - 기본 양념인 선택 재료는 뺀다.
    - 임박 재료는 D-3 이내만 넘긴다.
    - 직전 카드는 넘기지 않는다.
  - 분류·키워드가 있으면 요청 조건만 넣은 검색을 한 번 더 해서 합친다(각 최대 100건).
  - 합친 후보의 재료·정보는 한 번씩 읽는다.
  - ES 설정이 꺼졌거나 예외가 나면 WARN 로그를 남기고 기존 DB 경로로 간다.
- `5b43f8c8` 피할 맛을 빼서 3개 미만이면 `withoutAvoidTastes`로 다시 검색한다. 새로 나온 레시피를 피할 맛 레시피로 보고 뒤에 채운다.
- `a45dec2b` 키워드로 맞은 게 없을 때 벡터로 보충한다. 판단 기준과 횟수는 4번에서 바꿨다.
- `6e4ceeb6` 경로 로그를 남긴다: `상담 후보 모으기 - 경로: ES+요청만+벡터, 후보 n건 (...)`
- `9043537b` 말한 분류가 맞은 레시피도 1차 후보로 둔다.

### 2. 분류 단어 서버 확인 (`c188d408`)
- 원인 (세션 54): 콘솔 로그가 없어 dev DB에 저장된 메시지·카드와 로컬 Redis 직전 조건으로 맞춰 봤다.
  - 3번째·5번째 메시지에서 의도 결과의 분류·키워드·원한 표현이 모두 비어 있었다.
  - 그래서 냉장고 기준 4~6위가 나왔다. 1~3위는 앞에서 추천해서 뒤로 밀렸다.
  - "디저트는 없지만, 국과 찌개 요리를…"은 서버 안내가 아니라 AI가 쓴 소개 문장이다. 서버 안내는 요청 조건이 있을 때만 붙는다.
- `CategoryWordChecker`(신규): 메시지에 분류 이름이 단어로 있으면 원하는 분류, 부정어가 붙으면 피할 분류로 본다.
  - 단어가 분류 이름으로 시작하고, 남은 글자가 조사(은·는·이·가·을·를·도·만·랑·이랑·하고·나·이나·요리·류·종류·메뉴)거나 없어야 한다.
    - 국수·밥솥·전자레인지·김치찌개·찜닭은 분류로 보지 않는다.
    - "로·으로"는 재료로 쓰는 말("김치로")과 겹쳐 넣지 않았다.
  - 다음 단어가 요청하는 말(추천·먹·만들·말고·같이 …)이거나 메시지 끝이어야 한다. "김치 넣은", "떡 썰어서"를 빼려는 것이다.
  - "전"(저는)과 "밥"(끼니)은 서버가 채우지 않고 AI에 맡긴다.
  - 부정어는 맛 단어와 같은 기준이다(`TasteWordChecker`): 앞 "안·덜", 뒤 4글자 안 "말고·빼고·않·싫·없이"
- `ChatIntentFacade.correctCategories`:
  - 원하는 분류가 있으면 AI 결과보다 앞선다.
  - 직전 조건에서 끌려온 키워드·요리 이름(이번 말에 없는 것)은 뺀다.
  - 분류가 바뀌면 다시 추천(REFINE)에서도 직전 키워드를 잇지 않는다.
  - "디저트 말고"만 있으면 분류에서 빼고 직전 분류도 잇지 않는다.
  - 로그: `상담 분류 단어 확인 - 분류 채움|바꿈|그대로: AI [...] → [...]`

### 3. 후속 의도 프롬프트 (`bc193750`)
- 원인: 11-05 커밋 `9ce3ee62`(#585로 합쳐짐)에서 후속 프롬프트를 1,809자에서 1,169자로 줄였다(−35%).
  - 그때 분류 예시(`"국물 말고 볶음으로" → moodCategories: 볶음`)가 빠졌다.
  - "이번 말의 분류가 직전 조건보다 앞선다"는 규칙은 원래 없었다.
- 추가한 규칙:
  - 이번 말의 분류·요리 이름 우선
  - 같은 요청을 다시 해도 이번 말에서 다시 뽑기
  - 코스를 더하는 말("디저트도", "후식으로", "국도 같이")은 RECOMMEND
  - "다른·또·말고 다른"은 REFINE
- 예시 2줄: 김피탕 뒤 "디저트 추천해줘", 디저트 뒤 "다른 디저트", "다른 거", "디저트 말고 국"
- 길이: 1,169자 → 1,492자

### 4. "탕짜면" 관련
- `d4a78bb2` 프롬프트:
  - 레시피에 없을 법한 이름(줄임말·세트 메뉴·가게 메뉴·신조어)은 "같은"이 없어도 이루는 요리·비슷한 요리로 키워드를 늘린다.
  - 세트 메뉴는 구성 요리를 모두 넣고, 말한 이름은 dishText에 쓴다.
  - 줄임말 목록은 넣지 않았다.
  - 길이: 첫 질문 3,017자 → 3,134자, 후속 1,492자 → 1,569자
- `2b7827d7` 벡터 보충:
  - 원인: ES가 "탕짜면"을 "짜" 한 글자로만 잘라 간장게장·볶음쌀국수를 키워드 결과로 걸었다. 그래서 "키워드로 맞은 게 있다"고 보고 보충을 건너뛰었다.
  - 이제 보충 여부를 이름·늘린 이름·재료로 맞았는지(`KeywordMatch.strong`)로 정한다.
  - 키워드 결과로 표시되지 않은 후보도 이름에 요리 이름·키워드가 통째로 있으면 키워드로 맞은 것으로 본다. 아래 이름표 버그 우회다.
  - 벡터 검색은 키워드 순서대로 하다가 0건인 첫 키워드에서 한 번만 쓴다. 로그에 `+벡터`를 남긴다.
- `d1e6497f` 요리 이름 채우기:
  - AI가 dishText를 비웠는데 말에 그대로 있는 키워드가 고른 후보 레시피 이름에 없으면, 그 이름을 요리 이름으로 쓴다.
  - 그러면 "탕짜면 레시피는 없어서, 비슷한 탕수육과 볶음면을 골랐어요" 안내가 붙는다.
- `b801de47` 키워드별 고르기:
  - 키워드로 맞은 레시피가 두 키워드 이상이면 키워드마다 1장씩 먼저 고른다. 요리 이름이 맞은 것이 먼저이고, 그다음 AI 키워드 순서다.
  - 같은 분류 3개면 3위 교체는 정렬 순서로 채운 자리에만 한다. 키워드로 고른 자리는 바꾸지 않는다.
- `75ed5227` 다른 제안 표시: 3위 교체로 들어온 레시피가 키워드로 맞았으면 다른 제안으로 표시하지 않는다. 이유도 "색다르게" 대신 맞은 방식대로 쓴다.

### 5. 재료로 맞기 (`6f642539`)
- 원인: 기스면(205)이 키워드 "중국음식"과 재료 "중국부추"의 두 글자 겹침("중국")으로 [재료]가 됐다. 그래서 "탕짜면처럼 중국부추를 쓰는 요리예요"가 나왔다.
- 이제 키워드(두 글자 이상)가 재료 이름과 같거나 재료 이름에 통째로 있을 때만 [재료]로 본다. 버섯 ↔ 표고버섯은 계속 맞고, 일부만 겹치면 쪼개짐이다.

API·DB·프론트 변경 없음.

## 알려진 문제
- **레시피 담당 키워드 이름표 버그:** `RecipeCandidateSearchService`가 키워드마다 같은 이름(`keyword`)을 붙인다.
  - ES는 같은 이름이 여럿이면 마지막 것만 `matched_queries`에 돌려준다.
  - 서버는 후보 이름에 키워드가 통째로 있으면 맞은 것으로 보는 방식으로 우회했다.
  - 근본 수정(키워드 검색을 이름 하나로 묶기)은 레시피 담당에게 부탁할 항목이다.
- **ES 한 글자 쪼개짐:** 분석기가 "탕짜면"을 "짜"로만 남겨 상관없는 레시피(간장게장 등)를 키워드 결과로 건다.
  - 서버는 이름·재료가 통째로 맞은 것만 키워드 일치로 세서 영향을 줄였다.
- **레시피 데이터:** 짜장면·짬뽕 레시피가 없다. 세트 메뉴의 구성 요리를 키워드로 늘려도 한쪽(탕수육)만 찾힌다.

## 나중에 할 것
- "짬짜면"에 탕수육이 나온다. 짜장면·짬뽕 레시피가 없어 비슷한 요리로 늘린 키워드 중 탕수육만 맞는 것으로 보인다.
- 다른 제안 카드의 AI 설명이 가끔 빠진다.
- "냉메밀" ↔ 재료 "메밀면"은 이제 [재료]가 아니다(통째로 맞기 규칙). AI가 "메밀면"을 키워드로 따로 넣지 않으면 쪼개짐으로 분류된다.
- ~~매울 수 있음에 "고추"를 넣을지 정하기~~ 정확한 이름으로 넣음 (위 후속)
- DB 대체 경로를 언제 지울지 정하기
- 도메인 문서 반영 (따로 요청 예정)
