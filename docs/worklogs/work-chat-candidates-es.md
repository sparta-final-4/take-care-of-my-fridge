# 상담 후보 ES 검색 연결

상태: 검증 대기 · 작성일: 2026-11-06 · 담당: zcookiez

## 목표와 완료 기준
- 사용자 문제: AI 상담 추천 후보를 냉장고·선택 재료로 레시피를 역조회해서 모았다. 그래서 "디저트 추천해줘"처럼 분류만 말하면 냉장고와 겹치지 않는 디저트는 후보에 들지 못했다. 후보를 모으려고 냉장고 재료가 들어간 레시피 재료 줄을 모두 읽었다(회원 5번 기준 후보 1,281건).
- 확인 가능한 완료 조건:
  - 후보 모으기를 레시피 담당이 만든 ES 후보 검색(`RecipeCandidateSearchService`)으로 바꾼다. 정렬·카드 고르기·카드 이유는 그대로 둔다.
  - 분류나 키워드가 있으면 요청 조건만 넣은 검색을 한 번 더 해서 합친다.
  - 합친 후보의 재료·정보는 한 번씩만 읽는다.
  - 피할 맛으로 후보가 3개보다 적으면 다시 검색해서 채운다.
  - ES 장애 때나 ES를 쓰지 않는 설정이면 기존 DB 경로로 모은다.
  - 키워드로 맞은 레시피가 없을 때만 벡터 검색으로 보충한다.

## 근거와 범위
- 설계: 레시피 담당 작업 `856e57ca`(#590, 인덱스 필드)와 `f5818aea`(#591, 후보 검색)
- 변경할 영역: chat 도메인(`RecipeCandidateFacade`, `RecipeCandidateScorer`, `RecipeQuery`, 새 `RecipeCandidateConditions`)
- 다른 도메인 영향: search·recipe 코드는 바꾸지 않았다. 아래 "키워드 맞은 조건 이름 겹침"은 레시피 담당에게 수정을 부탁할 항목이다.
- 정한 정책:
  - 직전 카드는 ES에서 빼지 않는다. 지금처럼 `withoutPrevious`가 빼고, 3개 미만이면 다시 넣는다.
  - 이미 추천한 레시피는 지금처럼 정렬에서 뒤로 보낸다.
  - 기본 양념인 선택 재료는 검색 조건과 정렬에서 뺀다.
  - 임박 재료는 D-3 이내다.

## 계획
| 단계 | 변경 | 검증 |
|---|---|---|
| 1 | 정렬(`rank`)이 받은 후보 id를 그대로 쓰게 | 기존 정렬 테스트 + 냉장고와 안 겹치는 후보 정렬 |
| 2 | ES 후보 검색으로 모으기, 요청만 검색 합치기, DB 대체 경로 | 디저트·요청만 합치기·ES 실패·ES 꺼짐 |
| 3 | 피할 맛으로 3개 미만이면 다시 검색해 채우기 | 다시 채움·충분하면 다시 검색 안 함 |
| 4 | 키워드로 맞은 게 없을 때만 벡터 보충 | 벡터 보충·키워드 맞으면 보충 안 함 |
| 5 | 어디서 모았는지와 후보 수 로그 | 비교 실행 로그 |

## AI 활용과 개발자 판단
- AI에 맡긴 작업:
  - 레시피 담당 작업 조사
  - 내 RecipeQuery와 검색 조건 대조
  - 연결 방법 제안
  - 구현·테스트
  - dev DB(MySQL) + 로컬 ES로 두 방식 비교
- 채택한 제안:
  - 후보 모으기만 ES로 바꾼다.
  - 요청만 검색을 합친다. 냉장고 재료가 많이 겹치는 레시피에 분류만 맞은 레시피가 100건 밖으로 밀리지 않게 하려는 것이다.
  - 피할 맛은 3개 미만이면 다시 채운다.
  - ES 장애 때는 DB 경로로 간다.
  - 벡터는 키워드로 맞은 게 없을 때만 쓴다.
- 계획에 없던 변경: 말한 분류가 맞은 레시피도 1차 후보로 둔다. 따로 커밋했다.
  - 비교 결과, ES 후보에는 디저트 68건이 새로 들어왔지만 상위 10개에는 없었다.
  - 원인: 냉장고와 거의 안 겹치는 디저트는 보유 비율 기준 미만으로 2차 후보가 되고, 기준 이상인 다른 분류 레시피 10개에 가려졌다.
  - 키워드 이름·재료 일치를 1차 후보로 두는 것과 같은 대우로 맞췄다.
- 보류한 것:
  - 매울 수 있음(MILD)에 "고추" 넣기: 숫자만 확인하고 바꾸지 않았다.
  - DB 경로 코드 삭제: 대체 경로로 남겼다.
- 개발자가 확인한 근거:
  - dev DB 레시피 1,693개의 매운 정도 집계(아래)
  - 로컬 ES `recipes` 재색인 결과(HOT 431 / MILD 155)

## 구현 결과
- `RecipeCandidateConditions`(신규): RecipeQuery와 냉장고를 검색 조건으로 바꾼다.
  - 같은 종류 묶음을 펼친다.
  - 임박은 D-3 이내만 넘긴다.
  - 제외 분류는 설정값을 넘기고, 직전 카드는 넘기지 않는다.
  - 요청만 검색 조건은 냉장고·임박·원하는 맛 점수를 비우고 거르는 조건은 남긴다. 선택 재료만 쓰기면 선택 재료도 남긴다.
- `RecipeCandidateFacade`:
  - ES로 모은다(전체 + 요청만, 각 최대 100건).
  - 합친 후보로 `findNonBasicIngredients`·`findCandidateInfos`·맛·재료 이름을 한 번씩 읽는다. 부족한 재료는 읽은 재료를 다시 쓴다.
  - 키워드 결과 분류도 같은 레시피 정보를 쓴다. 그래서 DB 경로의 레시피 정보 조회도 두 번에서 한 번으로 줄었다.
  - ES 설정이 꺼졌거나 예외가 나면 WARN 로그를 남기고 기존 DB 경로로 간다.
- 피할 맛 다시 채우기: `withoutAvoidTastes`로 다시 검색해서, 처음 검색에 없던 레시피를 피할 맛 레시피로 보고 뒤에 채운다. 새로 나온 레시피만 더 읽는다.
- 벡터 보충: 키워드로 맞은 레시피가 없을 때 기존 레시피 검색을 부른다(글자 검색이 0건이면 벡터).
  - 이 후보는 ES 거르기를 거치지 않아, 정렬의 `isFilteredOut`과 피할 맛 처리에서 다시 거른다.
  - 기본 양념인 뺄 재료는 재료 줄에 없어 이 후보에서는 거르지 못한다.
- `RecipeCandidateScorer`:
  - `rank`가 후보 id를 받는다.
  - 말한 분류가 맞은 레시피도 1차 후보로 둔다.
- `RecipeQuery.withoutSelectedIngredients` 추가: 기본 양념인 선택 재료를 뺄 때 쓴다.
- 로그: `상담 후보 모으기 - 경로: ES+요청만, 후보 168건 (전체 100, 요청만 새로 68), 피할 맛 다시 채움 n건, 고른 후보 10건`
- API·DB·프론트 변경 없음.

| 조건 | 후보 수 (DB / ES) | ES 방식에만 / DB 방식에만 |
|---|---|---|
| 디저트 | 1,281 / 168 (요청만 새로 68) | 없음 / 없음. 두 방식 모두 디저트 10개(분류 1차 후보 커밋 뒤) |
| 김피탕·탕수육·깐풍기 | 1,282 / 100 | 배추겉절이·낙지연포탕·단호박배추된장국 / 탕수육·황태탕수육·가지 탕수육 (아래 이름 겹침 때문) |

| 피할 맛 SPICY | 1,281 / 100 | 없음 / 없음 |
| 30분 + 국 | 1,281 / 151 (요청만 새로 51) | 없음 / 없음 |

- 디저트는 분류 1차 후보 커밋 전에는 두 방식 모두 디저트가 0개였다. 대파 임박 레시피 10개가 차지했다.
- **키워드 맞은 조건 이름 겹침 (레시피 담당 수정 필요):** `RecipeCandidateSearchService`는 키워드마다 같은 이름(`keyword`)으로 검색을 건다.
  - ES는 같은 이름이 여러 개면 마지막 것만 `matched_queries`에 돌려준다. 로컬 ES에서 직접 확인했다.
  - 그래서 키워드가 2개 이상이면 마지막 키워드(깐풍기)만 키워드로 맞은 것으로 보인다. 탕수육은 후보에는 있지만 키워드 일치로 세지지 않아 밀린다.
  - 확인한 수정안: 키워드 검색을 하나의 `keyword` bool로 묶는다. 임시로 고쳐서 돌리면(커밋 안 함) 5개 조건 모두 두 방식 상위 10개가 같았다.

**매울 수 있음에 "고추"를 넣으면** (dev DB 레시피 1,693개, 재료 사전 이름·레시피에 적힌 이름, 공백 빼고, 풋고추·꽈리고추 제외)
- 지금 MILD 155개(9.2%) → 195개(11.5%), 40개 늘어난다.
- 늘어나는 재료 이름: 고추 23, 붉은고추 7, 실고추 6, 고추냉이 3, 오이고추 3, 다진고추·아삭이고추 2 등
- 고추냉이·오이고추·아삭이고추처럼 맵지 않은 것도 같이 걸린다. 이번에는 바꾸지 않았다.
