# 회원 도메인 설계

상태: 구현 완료 · 담당: 이현정 · 관련 화면: U-01~U-05, A-09, A-10 · API: [회원·인증·관리자 API 명세](../../api/member-auth-admin-api.md)

## 목적과 책임

- 해결할 사용자 문제: 회원이 이메일로 가입·로그인하고, 자기 정보와 맛 선호를 관리합니다. 관리자는 가입한 회원을 관리자로 승격하고 관리자 작업 이력을 봅니다.
- 이 도메인이 소유하는 데이터와 정책: 계정(이메일·비밀번호 해시·닉네임·전화번호·역할·상태), 맛 선호, 로그인 세션, 역할 검사, 관리자 작업 이력.
- 다른 도메인에 맡기는 책임: 후기 표시(후기), 주문 내역(주문), 냉장고(냉장고), 알림 수신(알림). 이 도메인은 닉네임·맛 선호·역할을 제공만 합니다.

## 상태와 전이

| 현재 상태 | 행동 | 조건 | 다음 상태 | 실패 |
|---|---|---|---|---|
| (없음) | 회원가입 | 이메일·닉네임·전화번호 미사용, 입력 규칙 통과 | ACTIVE, USER | 중복이면 해당 칸 오류, 계정 미생성 |
| ACTIVE | 로그인 | 비밀번호 일치 | ACTIVE, 세션 생성 | 불일치면 공통 실패 문구 |
| SUSPENDED | 로그인 | 비밀번호 일치 | 변화 없음 | 정지 안내, 세션 미생성 |
| ACTIVE · USER | 관리자 승격 | 요청자가 ADMIN | ACTIVE · ADMIN | USER가 요청하면 403, 작업 이력에 DENIED |
| SUSPENDED · USER | 관리자 승격 | | 변화 없음 | 승격 거부 |
| ACTIVE | 정지 | 처리 주체 미정 | SUSPENDED, 모든 세션 폐기 | 미정 |

세션 상태: 생성 → (30분 미사용 또는 7일 만료) 만료 → 로그아웃·비밀번호 변경(다른 기기)·정지 시 폐기(revoked_at 기록).

## 대표 흐름

- 첫 관리자: 환경변수 3개를 설정하고 서버를 시작하면 관리자 부재 시 전용 ACTIVE·ADMIN 계정을 생성한다. 기존 ADMIN이 있으면 변경하지 않는다. 설정 절차는 [첫 관리자 계정](#첫-관리자-계정)을 따른다.
- 정상 가입: 형식 확인 → 이메일 중복 확인 → 닉네임 중복 확인 → 계정 생성(ACTIVE·USER) → 맛 선호 저장 → 가입 완료 화면. 가입만 하고 로그인은 하지 않는다.
- 동시 가입: 두 사람이 같은 닉네임을 동시에 확인·가입하면 DB 유일 제약으로 한 명만 성공. 나머지는 중복 문구.
- 권한 거부: USER가 관리자 API를 호출하면 403, 데이터 변화 없음. 승격·할인 후보 실행·검토 저장은 서비스에서 역할을 검사해 작업 이력에 DENIED를 남긴다.
- 비밀번호 변경: 현재 비밀번호 확인 → 변경 → 다른 기기 세션 폐기. 현재 세션은 유지한다.
- 세션 만료: 401 → 프론트가 갱신 1회 시도 → 실패하면 U-05 "로그인 필요".

## 인증 쿠키·토큰·세션

쿠키 이름·경로·수명·속성과 CSRF 헤더는 [API 명세의 인증 쿠키](../../api/member-auth-admin-api.md#인증-쿠키)에 있습니다. 여기에는 동작을 적습니다.

- 토큰: 액세스·갱신 토큰은 JWT이고 서버 환경 변수 `JWT_SECRET`(UTF-8 32바이트 이상)으로 HS256 서명합니다. 액세스 토큰은 15분, 갱신 토큰은 최초 로그인부터 최대 7일입니다. 두 토큰 종류는 서로 바꿔 쓸 수 없습니다.
- 서버 세션: 로그인마다 `refresh_sessions` 행을 만들고, 액세스 토큰에 세션 ID를 담습니다. 갱신 토큰은 해시로만 저장합니다.
- 보호 API: `access_token`의 서명·만료·세션 ID를 확인한 뒤 회원 역할을 정합니다. 세션이 폐기·만료됐거나 30분간 쓰지 않았으면 401 `A003`입니다. 통과한 요청은 세션의 마지막 사용 시각을 갱신합니다.
- 갱신: 갱신 토큰은 쓸 때마다 새 토큰으로 바꿉니다. 같은 토큰으로 동시에 갱신하면 세션 행 잠금으로 한 요청만 성공합니다. 이미 바뀐 이전 토큰은 세션을 찾지 못해 401 `A005`입니다(그 세션을 폐기하지는 않음). 정지된 회원은 401 `A006`입니다. 바꿔도 최초 로그인부터 7일 한도는 늘지 않고, 새 갱신 쿠키 Max-Age는 남은 기간입니다.
- 갱신은 만료된 액세스 쿠키 없이도 되지만 `refresh_token` 쿠키와 CSRF 헤더가 필요합니다. 프론트는 동시 갱신을 한 번으로 모읍니다.
- 로그아웃: 액세스 쿠키가 유효하면 그 세션을, 만료됐으면 갱신 쿠키가 가리키는 세션을 폐기합니다. 쿠키가 없거나 이미 폐기·만료된 세션이어도 200이고 두 쿠키를 지웁니다.
- 권한: `/api/admin` 아래는 ADMIN만 씁니다. 익명은 401 `A003`, USER는 403 `A004`입니다. 403 `AUTH_002`는 CSRF 실패와 메서드 단위 권한 거부이며, 프론트는 CSRF 토큰을 다시 받아 한 번 재시도합니다.
- CSRF: 가입(`POST /members`)과 로그인(`POST /auth/login`)만 CSRF 검사에서 뺍니다. 프론트와 API가 같은 출처라 CORS 설정은 없습니다.

## 관리자 작업 이력

- 기록 대상: 승격(`ROLE_CHANGE`), 할인 후보 분석 실행(`DEAL_ANALYSIS`)·검토 저장(`DEAL_REVIEW`)·행사 등록(`EVENT_REQUEST`). 결과는 성공 SUCCESS, 실패 FAILED, 권한 없는 시도 DENIED입니다.
- 승격: 역할 변경과 성공 이력을 한 트랜잭션으로 저장합니다. 회원 목록의 `promotedAt`·`promotedBy`는 가장 최근 성공한 `ROLE_CHANGE` 이력에서 가져오며, 이력이 없는 관리자는 null입니다.
- 조회 기간: 기본은 오늘을 포함한 최근 7일입니다. `from`·`to`는 포함 날짜이고, `to`만 주면 그날까지 7일입니다. `from`이 `to`보다 늦으면 400입니다.
- 조회 결과: `result=FAILED`는 FAILED·DENIED를 함께 찾고, 최신 시각·ID 내림차순입니다. 작업 당시 역할(`actorRole`)과 민감 값을 뺀 바뀌기 전·후 값을 담습니다.
- 기록을 고치거나 지우는 API는 없습니다.

## 첫 관리자 계정

공개 회원가입은 USER만 만듭니다. 첫 ADMIN은 서버가 시작할 때 환경 변수로 한 번 만듭니다(`InitialAdminSeeder`). 비밀번호 값은 저장소에 커밋하지 않고 운영 환경이나 비밀 관리 시스템에 설정합니다.

| 변수 | 값 |
|---|---|
| `ADMIN_BOOTSTRAP_EMAIL` | 관리자 로그인 이메일. 가입과 같은 이메일 형식, 255자 이하, 다른 회원과 겹치지 않음 |
| `ADMIN_BOOTSTRAP_PASSWORD` | 가입과 같은 규칙: 8~30자, 영문·숫자·특수문자 모두 포함, 공백·한글 불가 |
| `ADMIN_BOOTSTRAP_NICKNAME` | 앞뒤 공백을 지운 뒤 1~30자, 다른 회원과 겹치지 않음. 지운 값으로 저장 |

서버 시작 때 이 순서로 확인합니다.

1. 세 값이 모두 없으면 아무것도 하지 않습니다.
2. 하나라도 없거나 빈 값(공백만 있는 값 포함)이면 시작이 실패합니다. ADMIN이 이미 있어도 실패합니다.
3. ADMIN이 이미 있으면 아무것도 하지 않습니다. 값의 형식·중복은 검사하지 않고, 새 계정을 만들거나 비밀번호를 바꾸지 않습니다.
4. 이메일·비밀번호·닉네임이 가입 입력 규칙에 어긋나면 시작이 실패합니다.
5. 이메일이나 닉네임이 기존 회원과 겹치면 시작이 실패합니다. 그 회원을 관리자로 바꾸지 않습니다.
6. ACTIVE·ADMIN 계정을 만듭니다. 전화번호는 비어 있습니다.

실행과 유지:

- 관리자 계정이 없는 DB에서 세 값을 설정하고 백엔드를 한 번 시작한 뒤, 일반 로그인 API로 로그인해 응답 역할이 ADMIN인지 확인합니다.
- 첫 생성이 끝나면 세 값을 함께 런타임에서 지웁니다. 하나만 남으면 2번에 걸려 시작이 실패합니다.
- 비밀번호는 로그인 뒤 회원 비밀번호 변경 API로 바꿀 수 있습니다.
- 서버 인스턴스가 여러 개면 한 인스턴스에서 관리자 생성을 마친 뒤 나머지를 시작합니다.

## 데이터·API·이벤트

- ERD·데이터 사전: [ERD](../../database/erd.md), [데이터 사전](../../database/data-dictionary.md)의 members, member_tastes, refresh_sessions, admin_audit_logs.
- 제공 API: [회원·인증·관리자 API 명세](../../api/member-auth-admin-api.md).
- 발행·수신 이벤트와 중복 처리: 없음. 후기는 회원 정보를 조회해 표시합니다.
- 보관 기간·삭제 정책: 회원 탈퇴가 없어 계정 삭제 없음. 폐기된 세션 정리 주기는 미정.

## 구현 방향

- 트랜잭션 범위: 회원 생성과 맛 선호 저장을 한 트랜잭션으로 묶습니다. 승격과 작업 이력 기록도 함께 커밋합니다.
- 동시성 제어 필요성과 근거: 중복 가입은 DB 유일 제약으로 막습니다. 동시 갱신은 세션 행 잠금으로 막습니다. 별도 분산 락은 두지 않습니다.
- 외부 I/O 및 실패 복구: 이메일 인증을 도입하면 메일 발송을 트랜잭션 밖(AFTER_COMMIT)으로 분리합니다.
- 권한 반영: 서버는 요청마다 DB의 역할로 권한을 검사하므로 승격은 바로 적용됩니다. 관리자 화면 전환은 대상 회원의 다음 로그인 때입니다.

## 남은 결정

- 이메일 인증 도입 여부 (Q-09 남은 질문).
- 계정 정지 처리 주체와 화면.
- 폐기된 세션 정리 주기.
- 상품 작업 이력을 누가 기록할지. 작업 이력의 `PRODUCT_CREATE`·`PRODUCT_DELETE`·`PRICE_UPDATE` 값은 있지만 상품 등록·삭제·정상가 수정에서 이력을 남기는 코드가 없습니다. 그래서 A-09 작업 이력과 A-02 상품 변경 이력에 상품 작업이 나오지 않습니다 (실제 기능 빠짐).

## 제안 기능

| 기능 | Method / Path |
|---|---|
