# 판매 예측용 주문 데이터 협의

상태: 검토 중 · 작성일: 2026-10-19 · 담당: 관리자·분석 (제공: 주문·환불)

## 확정된 집계 정책

- 판매일은 구매 확정일이 아니라 결제일이다. 상품별 판매 수량은 결제 완료 수량에서 취소·환불 수량을 뺀다.
- 조회 기준 시각 전에 발생한 환불은 원래 결제일의 판매 수량에서 차감한다. 이후 환불은 그 시각의 조회 결과에 영향을 주지 않는다.
- 지난주 실제 판매량을 월요일 06시에 확정해 저장한 뒤에는 변경하지 않는다. 그 이후 환불은 다음 예측의 과거 판매 이력 조회에 반영한다.
- `dataCutoffAt`은 예측 입력에 사용한 주문·환불 데이터의 마지막 기준 시각이다. 배치 실행 시각과 같다고 가정하지 않는다.
- 예측 입력은 일요일 18시에 마감하고 22시에 생성한다. 실제 판매량은 다음 주 월요일 06시에 확정한다.

## 주문·환불 도메인에 필요한 조회

- 같은 백엔드 내부의 서비스 메서드로 `from`, `to`(결제일 양끝 포함), `asOf`(조회 기준 시각)를 받는다. 외부 HTTP API는 필요하지 않다.
- 상품 ID, 결제일, 판매 유형, 순판매 수량을 반환한다. 판매 유형별 행은 예측 소비자가 상품·날짜별로 합산할 수 있다.
- `asOf`까지 결제 완료된 주문 상품 수량을 더하고, `asOf`까지 처리된 해당 상품의 취소·부분/전체 환불 수량을 뺀다. `asOf` 이후 상태 변경은 제외한다.
- 과거 `asOf`를 다시 조회할 수 없다면, 예측 입력을 생성 시점에 저장하는 대안을 주문·환불 담당자와 합의해야 한다.

## 현재 구현과 차이

- PR #87의 `OrderSalesService.getDailyProductSales(LocalDate from, LocalDate to)`는 `CONFIRMED` 주문의 `confirmedAt`을 기준으로 집계한다. `asOf`와 환불 차감이 없어 예측 입력으로 바로 사용할 수 없다.
- 구매 확정 처리 서비스도 아직 연결되지 않았다. 주문 상태 변경은 주문 도메인이 맡고, 예측 도메인은 집계 결과만 읽는다.

## 남은 합의

- 주문·환불 담당자가 조회 방식과 환불 이력 제공 방식을 확인해야 한다.
- 배치가 사용할 시간대 표기는 구현 전에 명시해야 한다.
- PyTorch 모델 사용은 결정했다. 실제 판매 데이터 학습·성능 평가는 18번에서 확인한다.
