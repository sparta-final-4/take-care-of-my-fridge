# 판매 예측용 주문 데이터와 배치

상태: 구현 중 · 갱신일: 2026-10-26 · 담당: 관리자·분석 · API: [판매 예측 API 명세](../../api/forecast-api.md)

## 집계 기준

- 판매일은 주문 도메인의 `confirmedAt` 날짜다. 구매 확정된 주문 상품 수량에서 해당 상품의 `COMPLETED` 환불 수량을 뺀다. 확정 전 완료된 부분 환불도 차감한다.
- `asOf`까지 구매 확정된 주문과 `asOf`까지 완료된 환불만 집계한다. 환불은 주문의 구매 확정일에 귀속한다. `REQUESTED`와 `FAILED`는 차감하지 않는다.
- 21번 실적은 대상 주가 끝난 다음 월요일 06:00(Asia/Seoul)을 기준 시각으로 한 번 확정한다. 이후 환불은 저장된 실적을 바꾸지 않고, 다음 예측의 과거 판매 이력 조회에만 반영한다.
- 18번 예측은 일요일 18:00(Asia/Seoul) 입력 마감, 22:00 실행이다. `dataCutoffAt`은 18:00이다. 실패하면 다음 주 월요일 06:00 전까지 매시간 재시도한다. 실적 확정 배치는 매시간 미확정 주를 확인해, 서버가 정해진 시각에 꺼져 있었더라도 원래의 월요일 06:00 기준으로 처리한다.

## 구현 방식

- 예측 영역의 읽기 전용 조회가 주문·환불 엔티티를 집계한다. 같은 백엔드 내부 호출이며 외부 HTTP API는 없다.
- Java 배치는 상품별 지난 28일 수량과 과거 8주 학습 표본을 만든다. 기준선(`baselineQty`)은 대상 주 직전 7일의 순판매 수량이다. 실제 판매 이력이 없는 경우 예측을 저장하지 않는다.
- 별도 Python 작업이 PyTorch 모델을 실제 이력으로 학습하고 다음 주 수량을 추론한다. 모델 파일은 대상 주별로 보관하고, Java는 모델 버전·입력 마감 시각·예측 수량을 `prediction_runs`와 `sales_forecasts`에 저장한다. 가상 데이터 표시값은 `false`다.
- Python 작업의 HTTP 포트는 호스트에 게시하지 않는다. 운영에서는 Java 앱과 작업을 같은 내부 네트워크에 연결하고 `FORECAST_WORKER_URL`을 설정해야 한다.
- 운영 Java 이미지의 JVM 시간대를 `Asia/Seoul`로 고정한다. 주문·환불에서 새로 기록하는 `LocalDateTime.now()`와 배치의 기준 시각을 맞춘다. 이미 다른 시간대로 저장된 값은 이 설정만으로 변환되지 않는다.



## 조회 기준

- 화면(A-04·A-05)은 조회만 합니다. 예측 생성과 실적 확정은 위 배치가 합니다.
- 주간·최신 조회는 실제 예측만 돌려줍니다. `previousWeekStart`·`nextWeekStart`는 실제 예측이 있는 이전·다음 주입니다.
- 최신 예측이 없을 때 404 `F001` 메시지에는 대상 주, 입력 마감, 예측 대상 상품 수, 최근 84일 순판매 수량, 학습 표본 수, 마지막 배치 시도 상태를 담습니다. 배치 기록 도입 전 주차는 시도 기록이 없을 수 있습니다.
- dev 시연 결과는 `syntheticData=true`로 저장하고 `/admin/forecasts/demo`로만 봅니다. 실제 예측 배치의 대상 주와 겹치지 않는 지난 주차에 저장합니다.
- 요약의 `baselineMeanAbsoluteError`는 예상 TOP 10 상품의 |기준선 − 실제| 평균이며, 실제 판매량이 비어 있으면 0으로 계산합니다.

## 남은 검증

- MySQL에서 구매 확정·부분 환불 집계 쿼리 검증.
- PyTorch 작업의 컨테이너 빌드와 Java↔Python 통합 실행, 운영 네트워크 설정.
- 실제 운영 이력으로 모델 품질을 평가하기 전까지 예측 정확도를 보장하거나 운영 성과로 표현하지 않는다.
