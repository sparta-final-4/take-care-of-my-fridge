# 할인 후보 분석 입력 협의안

상태: 담당 도메인과 협의 전 · 작성일: 2026-10-20 · 담당: 관리자·분석

이 문서는 23번 협의를 위한 요청안이다. 아래 제공 방식과 계산 기준은 아직 합의되지 않았으며, 이 문서만으로 24번 분석 실행을 구현하지 않는다.

## 분석이 받을 입력

같은 백엔드 안의 서비스 메서드로 분석 대상 상품 목록과 지표를 받는 방안을 제안한다. 관리자 화면을 위한 별도 HTTP API는 필요하지 않다. 모든 입력은 상품 ID로 연결하고, 분석 실행 시각과 각 데이터의 기준 시각을 저장한다.

| 제공 영역 | 제안하는 반환값 | 단위·기준 |
|---|---|---|
| 상품 | 상품 ID, 상품명, 정상가, 판매 상태 | 가격은 원 단위 정수. 판매 가능한 상품만 후보 대상인지 확인 필요 |
| 재고 | 상품 ID, 현재 재고, 재고 기준 시각 | 수량은 개 단위. 상품 목록과 같은 시점의 스냅샷을 만들 수 있는지 확인 필요 |
| 검색·추천 | 상품 ID, 최근 4주 같은 요일 검색 클릭 수·구매 수, 집계 기준 시각 | 클릭과 구매의 이벤트 정의, 중복 집계 방식 확인 필요 |
| 주문·환불 | 상품 ID, 최근 4주 같은 요일 순판매 수량과 기준 시각 | 결제일 기준 수량에서 기준 시각까지의 취소·환불 차감. 21번과 같은 조회 의존성 |
| 할인 수요 계산 | 정상가 예상 수량, 요청 할인율 적용 시 예상 수량, 모델 버전, 가상 데이터 여부 | 10·20·30·40% 할인별 예상 증가량 산출 방식 확인 필요 |

## 담당자에게 확인할 결정

1. 상품·재고 담당: 상품명·정상가·판매 상태·재고를 한 시점에 읽는 메서드를 제공할 수 있는가? 분석 중 값이 바뀌면 어떤 스냅샷을 기준으로 할 것인가?
2. 검색·추천 담당: `searchClicks`는 검색 결과 클릭 횟수인가? `purchases`는 검색 이후 구매 전환인가, 해당 상품 전체 구매인가? 동일 사용자의 반복 클릭과 취소·환불은 어떻게 처리하는가?
3. 주문·환불 담당: 결제일과 `asOf` 기준의 순판매 수량을 최근 4주 같은 요일별로 제공할 수 있는가? 판매가 없는 날은 0으로 포함하는가?
4. 분석 담당: `TOP_SELLER_ON_DAY`를 상위 몇 개 또는 몇 %로 판정하는가? `LOW_STOCK`은 `currentStock < minStock`인가? 둘 다 해당하면 어느 제외 사유를 우선하는가?
5. 분석 담당: `expectedQtyRegular`·`expectedQtyDiscount`를 계산할 모델 또는 검증된 규칙은 무엇인가? 할인가 예상 수량이 재고보다 크면 어떻게 처리하는가?
6. 각 담당: 입력 기간의 종료 시각과 시간대, 누락된 지표 처리(제외·실패·0 대체), 장애 시 재시도 책임을 정한다.

## 현재 코드에서 확인한 차이

- 상품 엔티티에는 ID·상품명·가격·상태·재고가 있지만, 분석용 일관된 기준 시각 스냅샷 메서드는 없다.
- 검색 도메인에는 집계 지표 구현이 없다.
- 기존 주문 판매 조회는 구매 확정일 기준이고 `asOf`·환불 차감이 없어 요일별 순판매 입력으로 사용할 수 없다.
- 할인율에 따른 예상 판매 수량 계산 모델과 행사 담당 기능은 아직 없다.

## 연결 순서

담당자 답변으로 필드·단위·시점을 확정한 뒤 제공 메서드를 연결하고, 후보/제외 판정과 예상 증가량 계산을 구현한다. 실행 결과가 생성되면 저장·조회·검토 기능에 연결한다. 선택된 후보의 행사 등록은 기존 행사 생성 서비스에 직접 연결하며, 생성된 행사 ID를 후보에 기록한다.
