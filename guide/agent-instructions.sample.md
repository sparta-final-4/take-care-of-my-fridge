# AGENTS·CLAUDE 지침 작성 예시

> **학습용 가상 예시** — 실제 구현·팀 결정·테스트 결과가 아닙니다. 상품 논리 삭제 기능의 설계가 구체화된 상황을 가정했습니다. 실제 문서로 옮길 때 정책과 증거를 다시 확인하세요.

**읽는 법**: 실제 AGENTS.md·CLAUDE.md를 대체하는 규칙이 아닙니다. 지침 파일은 “개발 이력”보다 “작업 시작과 완료 절차”를 적습니다.

## 루트 AGENTS에 넣을 내용 예

1. 작업 시작 전에 관련 요구사항 ID와 화면 ID를 확인한다.
2. API 변경이면 서버 DTO·프론트 타입·API 명세를 함께 읽는다.
3. 상품 삭제 작업은 상품과 해당 관리자 화면을 기본 범위로 한다. 주문 코드 변경이 필요하면 사유·범위와 기존 승인 여부를 확인한다.
4. 예정 경로와 실제 코드를 구분하고, 미확정 정책을 임의로 구현하지 않는다.
5. 완료 보고에는 실제 검증 결과와 관련 문서 변경을 포함한다.

구체적인 삭제 상태·응답 코드는 도메인·API 문서로 연결한다. 매 기능의 정책을 AGENTS에 계속 쌓지 않는다.

---

## frontend/AGENTS에 넣을 내용 예

A-01·A-02 화면 동작, DELETE 계약, API 모듈·조회 키를 확인한다. 삭제 mutation 성공 시 상품 목록·상세 캐시를 무효화한다. 확인 모달·중복 클릭·오류 안내와 반응형을 검증한다. 정확한 구현 경로는 실제 코드 확인 후 기록한다.

---

## backend/AGENTS에 넣을 내용 예

상품 상태 전이, 권한, 감사 기록, 기존 주문 스냅샷 계약을 읽는다. 트랜잭션 내 삭제 상태와 성공 감사의 일관성, 재요청·동시 충돌 처리를 검증한다. 테스트에서 생성한 데이터를 운영 데이터로 간주하지 않는다.

---

## CLAUDE 진입점에 넣을 내용 예

“같은 디렉터리의 AGENTS.md와 연결된 상세 규칙을 읽는다. 공통 규칙은 루트 AGENTS.md를 따른다.”

규칙 본문을 두 도구용 파일에 각각 복사하지 않고 경로 안내를 유지한다.

## 실제 반영 체크

지침에 적힌 명령이 실제 package.json·Gradle과 일치하는지, 링크 대상이 있는지, 팀 승인이 필요한 범위를 명확히 적었는지 확인한다.
