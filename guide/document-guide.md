## API 계약

대상: [docs/api/api-spec.md](../docs/api/api-spec.md) · 현재 수준: **공통 규격·기능 목록·양식 있음**

| 구분 | 내용 |
|---|---|
| **역할** | 프론트와 백엔드가 같은 요청·응답을 구현하도록 정하는 약속입니다. |
| **작성할 내용** | HTTP 메서드·경로, 인증·권한, 경로·쿼리·본문 필드의 타입·필수·null·범위, 성공 응답, 오류 코드, 페이지·정렬, 재요청·동시성 처리를 API별로 적습니다. |

| **작성 시점** | 연동 구현 전에 합의하고 계약 변경 때 갱신합니다. 프론트가 필드나 오류 동작을 추측하지 않아도 되는 수준으로 씁니다. |

## ERD 초안

대상: [docs/database/erd.md](../docs/database/erd.md) · 현재 수준: **개인 담당 8개 테이블 관계도 있음**

| 구분 | 내용 |
|---|---|
| **역할** | 저장할 데이터의 개체와 관계를 그림으로 설명합니다. |
| **작성할 내용** | 테이블 또는 개념 이름, PK·FK, 1대다 등의 관계, 필수·선택 여부, 삭제 시 관계 처리, 도메인 경계를 적습니다. 개념도인지 실제 테이블 설계인지 표시합니다. |
| **현재 내용** | 개인 담당 테이블 8개(members, member_tastes, refresh_sessions, prediction_runs, sales_forecasts, deal_analyses, deal_candidates, admin_audit_logs)의 관계도와 관계별 필수 여부가 있습니다. 상품·할인 행사처럼 FK 없이 ID만 저장하는 외부 참조와, 회원·후기·주문·환불 등 연동 시 확인할 관계도 적혀 있습니다. |
| **보완할 내용** | 다른 도메인의 테이블은 아직 없어 전체 ERD가 아닙니다. 각 담당의 테이블이 생기면 연결하고, 외부 참조에 물리 FK를 걸지 결정합니다. 삭제 정책과 인덱스도 정해야 합니다. |
| **작성 시점** | 데이터 모델을 정할 때 작성합니다. 실제 DB와 대조할 수 있는 물리 모델이 되기 전에는 ‘초안’ 표시를 유지합니다. |

## 지금 무엇부터 채우면 되나요

1. 기획서의 MVP·담당·미결정 정책부터 합의합니다.
2. 먼저 구현할 화면의 상세 동작을 채웁니다.
3. 해당 도메인 설계·API·ERD·데이터 사전을 함께 맞춥니다.

필요할 때만 [참고 예시 목록](README.md#참고용-예시)을 확인하세요. 예시의 정책·성과는 현재 문서의 작성 현황에 포함하지 않았습니다.
