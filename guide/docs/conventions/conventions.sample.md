# 프론트·백엔드·DB·Git 규칙 적용 예시

> **학습용 가상 예시** — 실제 구현·팀 결정·테스트 결과가 아닙니다. 상품 논리 삭제 기능의 설계가 구체화된 상황을 가정했습니다. 실제 문서로 옮길 때 정책과 증거를 다시 확인하세요.

**읽는 법**: 이미 긴 상세 규칙을 더 복제하기보다, 같은 기능에서 각 규칙이 어떤 역할을 하는지 보여줍니다. 실제 네 개의 conventions 문서를 작성할 때도 “규칙·이유·적용 예”를 연결하면 좋습니다.

## frontend.md 작성 예시

| 항목 | 내용 |
|---|---|
| **규칙** | 서버 데이터는 TanStack Query로 관리한다. |
| **이유** | 삭제 후 목록·상세를 동일한 서버 상태로 다시 조회하기 위해서다. |
| **적용 예** | 삭제 API 성공 시 상품 목록·상세 queryKey를 무효화하고, 버튼을 요청 중 비활성화한다. |
| **검증** | 성공·403·409에서 모달과 목록 상태가 의도대로 변하는지 확인한다. |

코드 위치는 실제 구현 후 적는다. 예시에서 새 컴포넌트 파일을 구현된 것처럼 링크하지 않는다.

## backend.md 작성 예시

| 항목 | 내용 |
|---|---|
| **규칙** | Controller는 권한·입력·응답 경계를, Service는 상태 전이와 트랜잭션을 담당한다. |
| **적용 예** | 인증된 ADMIN 요청에서 상품을 조회하고 삭제 메서드로 상태를 바꾼다. 성공 감사와 상품 상태는 함께 커밋한다. |
| **예외** | 권한 거부는 비즈니스 서비스 진입 전에도 발생하므로 거부 감사의 기록 경로를 별도로 정의한다. |
| **검증** | 실패했을 때 상품만 삭제되거나 성공 감사만 남는 불일치를 확인한다. |

## database.md 작성 예시

| 항목 | 내용 |
|---|---|
| **공통 규칙** | snake_case, BIGINT PK, 감사 시각과 한국어 설명. |
| **예시 선택** | products에 status·deleted_at·version을 둔다. 물리 타입과 NULL 여부는 데이터 사전에 적는다. |

- 예시에서는 UTC·JPA 감사 관리를 가정했다. 이는 실제 프로젝트의 DB 자동 갱신 규칙을 변경하는 승인이 아니다.
- 구체적인 인덱스는 해당 조회 조건과 실행 계획을 보고 결정한다.

## git.md 작성 예시

| 항목 | 내용 |
|---|---|
| **커밋 예시 문구** | “feat: 관리자 상품 논리 삭제 추가”. 실제 커밋이 존재한다는 의미가 아니다. |
| **PR 설명 예시** | “삭제 후 고객 목록에서는 제외하고 관리자 목록과 과거 주문은 유지하도록 변경. 재요청 및 권한 거부 시나리오를 포함.” |
| **검증란** | 실행한 명령·결과와 미실행 사유를 기입한다. 자동으로 “전체 통과”를 넣지 않는다. |
| **리뷰** | 정책·API·테스트·문서가 같은 삭제 동작을 설명하는지 확인한다. |

병합·배포 기준은 팀이 합의한 실제 정책을 사용한다.
