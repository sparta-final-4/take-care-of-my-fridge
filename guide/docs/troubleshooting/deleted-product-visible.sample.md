# 삭제한 상품이 고객 목록에 남는 문제 — 조사 기록 예시

> **학습용 가상 예시** — 실제 발생한 사건·팀 결정·검증 결과가 아닙니다. 서술 방식과 필요한 근거를 설명하기 위한 사례입니다. 실제 증거가 없는 부분을 완료 실적으로 제출하지 마세요.

**읽는 법**: 아래는 발생 가능한 문제를 가정한 연습 사례입니다. 실제로 겪지 않았다면 본인의 문제 해결 사례로 옮기지 않습니다.

| 항목 | 내용 |
|---|---|
| **실제 상태** | 재현·검증 미실행. |
| **가상 증상** | 관리자 삭제가 성공했는데 새로 조회한 고객 상품 목록에 계속 나타남. |
| **가정한 영향** | 고객이 판매 중지 상품을 선택할 수 있어 화면과 운영 상태가 불일치함. |

---

## 재현 절차 예시

1. ON_SALE 일반 상품을 생성한다.
2. ADMIN으로 삭제한다.
3. DB에서 DELETED와 삭제 시각을 확인한다.
4. 브라우저 캐시와 무관하게 고객 목록 API를 새로 호출한다.
5. 응답에 대상이 포함되는지 확인한다.

현재 프로젝트에서는 위 절차를 실행하지 않았다.

---

## 원인 후보와 조사 방법

| 가설 | 확인할 것 | 원인으로 볼 수 있는 관찰 |
|---|---|---|
| 화면 캐시가 남음 | 새 API 응답과 화면 비교 | 응답에는 없고 화면에만 남음 |
| 삭제 저장 실패 | 삭제 응답·DB 상태 확인 | DB가 ON_SALE로 남음 |
| 조회 조건 누락 | 신규 조회 응답·쿼리 조건 | DB는 DELETED인데 새 API 응답에 포함 |

이 예시의 설명 흐름에서는 세 번째 관찰이 확인됐다고 **가정**한다. 실제 조사 결과가 아니다.

---

## 가상 원인·수정안

사용자 상품 조회가 상태 조건 없이 모든 상품을 반환했다고 가정한다. 사용자 조회에 판매 가능 상태 조건을 적용하고 관리자 조회는 삭제 상품을 볼 수 있도록 분리한다.

프론트에서 결과를 숨기는 것만으로 해결하지 않는다. 실제 데이터 제공 경로의 조건을 확인해야 한다. 기존 검색·추천도 같은 조회를 쓰는지는 확인 후 영향 범위를 정한다.

## 재검증 계획

T-08로 사용자 목록 제외, T-04로 관리자 목록·주문 보존을 확인한다. 상품 조회 필터·페이지 수가 올바른지도 기존 테스트로 확인한다.

실제 결과: 미실행. 수정 커밋·로그·화면 증거: 없음.
