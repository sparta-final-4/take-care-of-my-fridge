# ADR-001: 상품 삭제를 상태 변경으로 처리 — 예시

> **학습용 가상 예시** — 실제 발생한 사건·팀 결정·검증 결과가 아닙니다. 서술 방식과 필요한 근거를 설명하기 위한 사례입니다. 실제 증거가 없는 부분을 완료 실적으로 제출하지 마세요.

**읽는 법**: ADR은 구현 절차보다 선택 이유를 담습니다. 아래의 “선택”은 예시 안에서만 유효합니다.

| 항목 | 내용 |
|---|---|
| **상태** | 예시 내 선택안, 실제 프로젝트 미채택. |
| **작성일·결정자** | 실제 의사결정 없음. |
| **관련 요구** | REQ-PRODUCT-DELETE-02·03. |
| **배경** | 판매 중단 후에도 관리자 확인과 기존 주문 정보 조회가 필요하다. |

---

## 대안 비교

| 방법 | 장점 | 비용·위험 |
|---|---|---|
| 물리 삭제 | 사용자 목록에 남을 위험 감소 | 참조·이력 보존 정책이 별도로 필요 |
| 상태·삭제 시각 기록 | 기존 행·참조 유지, 관리자 조회 가능 | 사용자 조회에서 삭제 제외 조건 누락 가능 |
| 별도 보관 테이블 이동 | 운영 데이터와 과거 데이터 분리 | 이동·참조·조회 구현과 일관성 관리 증가 |

---

## 예시의 선택

상품 행을 유지하고 status=DELETED와 deleted_at을 기록한다. 관리자가 같은 목록에서 판매 중지 상태를 확인해야 하므로 별도 보관 테이블보다 구조가 단순하다.

과거 주문 이름·가격은 주문 생성 시 스냅샷으로 보존한다. 논리 삭제만으로 가격 변경 이력까지 보호되는 것은 아니다.

---

## 받아들이는 비용

모든 사용자 조회 경로에서 판매 가능 상태를 확인해야 한다. 관리자 조회까지 전역 필터로 숨기면 삭제 상품을 확인할 수 없으므로 조회 목적에 따라 정책을 명시한다.

물리 데이터 정리·보관 기간은 이 선택으로 해결하지 않는다. 별도 정책이 필요하다.

---

## 검증 계획과 실제 결과

| 구분 | 내용 |
|---|---|
| **계획** | 삭제 후 사용자 목록 제외, 관리자 목록 유지, 과거 주문 스냅샷 불변, 재요청 시각 불변. |
| **실제 결과** | 미실행. |

관련 [테스트 계획](../testing/test-strategy.sample.md)의 결과와 실제 커밋·PR을 연결한 후 근거를 보완한다.

---

## 재검토 조건

법적·운영적 보관 요구가 확정되거나 조회 경로 증가로 삭제 조건 누락이 반복되면 보관·조회 전략을 다시 검토한다. 실제 결정이 바뀌면 이력을 지우기보다 대체 ADR을 연결한다.
