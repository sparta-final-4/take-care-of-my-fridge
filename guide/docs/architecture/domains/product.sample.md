# 상품 도메인 — 논리 삭제 설계 예시

> **학습용 가상 예시** — 실제 구현·팀 결정·테스트 결과가 아닙니다. 상품 논리 삭제 기능을 가정한 문서이며, 실제 프로젝트에 적용하기 전 정책과 증거를 확인하세요.

**읽는 법**: 도메인 템플릿의 “정책·상태·흐름”을 채운 예입니다. 상품 등록·가격 변경 등 전체 도메인 기능은 생략한 발췌입니다.

## 목적과 책임

상품 도메인은 고객에게 판매할 상품의 상태를 관리한다. 기존 주문의 표시 데이터는 주문 도메인의 스냅샷이 책임진다. 상품 삭제는 주문 취소·환불을 호출하지 않는다.

---

## 정책·상태 전이

| 현재 상태 | 요청·조건 | 결과 | 저장 변화 |
|---|---|---|---|
| ON_SALE | ADMIN 삭제 | 200 | DELETED, deleted_at 설정, version 증가 |
| DELETED | ADMIN 재요청 | 200 | 시각·version·성공 감사 유지 |
| 임의 상태 | USER 요청 | 403 | 상품 변경 없음 |
| 없음 | ADMIN 삭제 | 404 | 상품 변경 없음 |
| ON_SALE | 동시에 다른 변경이 커밋됨 | 409 | 충돌한 요청 롤백 |

삭제 시각은 최초 삭제 시점이다. 복구는 이 예시 범위에 없다. 상태와 deleted_at의 조합이 모순되지 않도록 도메인 메서드로 변경한다.

---

## 정상 흐름

1. 인증 경계에서 ADMIN인지 확인한다.
2. 상품을 조회한다. 없는 경우 404.
3. 이미 DELETED면 성공 응답으로 종료한다.
4. 삭제 상태·시각을 설정한다.
5. 작업자·대상·전후 상태를 성공 감사로 저장한다.
6. version 충돌 없이 트랜잭션이 커밋된 뒤 성공 응답을 반환한다.

---

## 동시성·실패

일반 상품 삭제에는 재고 계산이 없어 별도 분산 락을 두지 않는 예시다. version 충돌이면 409이며, 화면이 새 상태를 확인하도록 한다. 나중에 재요청해 이미 DELETED를 읽으면 200이다. “동시 충돌한 요청”과 “삭제 완료 후 재요청”을 구분한다.

권한 거부 감사는 인증된 행위자와 요청 대상을 기록한다. 성공 감사와 다른 처리 경로이며, 구체적인 감사 저장소 전체 스키마는 이 발췌의 범위 밖이다.

---

## 조회·연동

| 조회 대상 | 정책 |
|---|---|
| **사용자 상품 목록** | DELETED 제외. |
| **관리자 목록** | 상태 필터를 통해 DELETED 포함. |
| **주문 상세** | 상품의 현재 이름·가격을 덮어쓰지 않고 기존 스냅샷 사용. |
| **행사 연결 상품** | 별도 정책 미확정, 예시 시나리오에서 제외. |
