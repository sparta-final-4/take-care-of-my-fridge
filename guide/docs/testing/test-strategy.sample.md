# 상품 삭제 테스트 전략 — 구체적 시나리오 예시

> **학습용 가상 예시** — 실제 발생한 사건·팀 결정·검증 결과가 아닙니다. 서술 방식과 필요한 근거를 설명하기 위한 사례입니다. 실제 증거가 없는 부분을 완료 실적으로 제출하지 마세요.

**읽는 법**: 테스트 이름만 적지 말고 사전 상태·행동·기대 결과를 적습니다. 아래 결과는 모두 미실행입니다.

## 테스트 데이터 조건

ADMIN 1명, USER 1명, 행사에 연결되지 않은 ON_SALE 상품, 별도의 DELETED 상품, 삭제 대상 상품의 기존 주문 상품을 준비한다. 데이터는 테스트 전용이며 현재 저장소에 생성되어 있지 않다.

## 시나리오

| ID | 입력·행동 | 기대 결과 | 수준 | 실제 결과 |
|---|---|---|---|---|
| T-01 | ADMIN이 ON_SALE 상품 삭제 | 200, DELETED·deleted_at, 최초 성공 감사 | API·DB 통합 | 미실행 |
| T-02 | USER가 같은 API 호출 | 403, 상품 불변, 거부 기록 | 보안 통합 | 미실행 |
| T-03 | 인증 없이 API 호출 | 401, 상품 불변 | 보안 통합 | 미실행 |
| T-04 | 상품 삭제 전후 기존 주문 조회 | 이름·단가·수량 동일, 관리자 목록 유지 | 도메인 연동 | 미실행 |
| T-05 | 삭제 완료 후 같은 요청 반복 | 200, 삭제 시각·성공 감사 수 불변 | 통합 | 미실행 |
| T-06 | 같은 version을 읽은 두 갱신 경합 | 한 갱신 후 나머지 충돌은 409, 불일치 없음 | 동시성 통합 | 미실행 |
| T-07 | 최초 성공 감사 저장 실패 유도 | 상품 변경도 롤백, 성공 응답 없음 | 트랜잭션 통합 | 미실행 |
| T-08 | 삭제 후 사용자 상품 목록 조회 | 대상 제외, 다른 판매 상품 유지 | 조회 통합 | 미실행 |

없는 ID의 404, 잘못된 ID의 400도 API 계약 검증에 포함한다. 사용자 목록 외 검색·추천 경로는 실제 존재 여부와 담당 계약을 확인해 범위를 추가한다.

## 화면 확인

삭제 확인·취소, 요청 중 중복 클릭, 200 후 재조회, 403 안내, 409 후 상태 갱신, 네트워크 실패 표시를 확인한다. 375 / 768 / 1440px와 키보드 조작을 실제 브라우저에서 확인한다.

## 명령과 증거

| 대상 | 실행할 명령 | 실제 결과 |
|---|---|---|
| 프론트 | pnpm lint / format:check / typecheck / build / test | 미실행 |
| 백엔드 | ./gradlew clean compileJava compileTestJava | 미실행 |
| 백엔드 테스트 | ./gradlew test | 미실행 |

명령은 해당 프로젝트 설정이 있을 때 실제 스크립트와 대조한다. Windows 백엔드는 gradlew.bat를 사용한다.

실제 실행 후 기록할 값: 런타임·DB 버전, 대상 커밋, 테스트 데이터, 정확한 명령, 결과 로그 위치, 실패 원인. 통과 수는 실제 출력에서 가져온다.
